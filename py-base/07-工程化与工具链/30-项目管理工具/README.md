## 0. 依据标注约定

本章 `` `[Rn]` `` 仅在本章有效，索引见第 7 节；「未直连核对」的链接按官方文档通行表述整理。**本课不安装任何工具、不生成锁文件。**

## 1. 概念

- **锁文件**记录解析后的精确版本（常含哈希与来源），与「声明意图」的 `requirements.txt` / `pyproject.toml` 分开；`pip freeze` **不是** lockfile（第 02 章已确认）。`[R1]`
- PEP 751 定义了 `pylock.toml` 这一互操作锁文件格式，目标是让不同工具能消费同一份锁定结果。`[R2]`
- 现代项目管理工具（uv / Poetry / PDM / Hatch）通常同时提供：虚拟环境管理、依赖解析与锁定、构建后端、任务运行器。`[R3]`
- **依赖组**：运行时依赖、开发依赖、文档/测试依赖分开，避免把测试框架装进生产镜像。`[R3]`
- 工具选型看四项：维护活跃度、锁文件与离线安装能力、与现有 CI/构建链契合度、退出成本（第 01 章）。
- 关键依赖登记备选方案，避免被单一工具锁死（第 01 章）。

## 2. 注意事项

1. **锁文件必须入库**，且变更要随依赖变更一起 review。`[R3]`
2. **不要把锁文件当手改配置**，由工具生成。
3. **生产安装用锁定结果**，不要在部署时重新解析最新版。
4. **不要在一个项目里混用两套工具的锁文件**。`[R3]`
5. **升级工具本身也要评估**：解析器行为变化会产生大规模锁文件 diff。
6. **不要跳过安全审计**：定期扫依赖漏洞与 EOL（第 23 章）。

## 3. 边界考虑

| 边界 | 说明 | 依据 |
| --- | --- | --- |
| 跨平台锁定 | 不同平台/Python 版本解析结果可能不同，需要多平台策略 | `[R3]` |
| 哈希与来源 | 锁定可带哈希校验，但私有 index 的可用性要一并考虑 | `[R1]` |
| 与 pip 兼容 | `pylock.toml` 是规范，工具支持程度随时间变化 | `[R2]` |
| 单仓多包 | workspace 需求见第 31 章 | `[R3]` |

## 4. 最佳实践

1. **一个项目一个工具、一个锁文件、一条安装命令**。
2. **CI 用「锁定安装 + 校验锁文件未漂移」**。
3. **开发/运行依赖分组**，生产镜像只装运行时组。`[R3]`
4. **定期、小步升级依赖**，不要攒大版本。
5. **把工具版本也写进配置**，保证团队一致。

## 5. 最佳编码建议

- **命令写进任务运行器**，不要散落在 README 里让人手抄。
- **注释解释「为什么选这个工具 / 为什么锁这个版本」**。`[R4]`
- **配置外置、密钥不进锁文件**（第 01 章）。
- **不做预留扩展、KISS**（第 01 章）。

## 6. 编码示例

`examples/tooling_demo.py`（只读探测本机有哪些工具，输出因机器而异）：

```python
"""第 30 章示例：只读检查本机可用的项目管理工具。"""

import shutil

for name in ["python", "pip", "uv", "poetry", "pdm", "hatch"]:
    print(name, "->", shutil.which(name) is not None)
```

运行：

```powershell
cd 'E:\ai-agent-study\py-base\07-工程化与工具链\30-项目管理工具'
python examples/tooling_demo.py
```

关键输出：`python` / `pip` 为 `True`，其余取决于本机是否安装——这是只读探测，不会改动环境。`[R3]`
