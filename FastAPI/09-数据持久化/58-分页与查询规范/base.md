## 1. 概念：O(offset) vs O(limit)

| 方案 | 数据库实际动作 | 成本 |
| --- | --- | --- |
| `LIMIT 20 OFFSET 99000` | 沿索引**走过** 99000 条，丢弃 | O(offset + limit) |
| `WHERE (ts,id) < (?,?) LIMIT 20` | 索引**定位**到该位置，取 20 条 | O(limit) |

实测（10 万行）：

| 查询 | 耗时 |
| --- | --- |
| `OFFSET 0` | 0.055ms |
| `OFFSET 99000` | 7.294ms（133×）|
| 游标首页 | 0.038ms |
| 游标深页 | 0.058ms |

**结论**：offset 随页码线性变慢，游标恒定。

## 2. 机制：索引怎么支撑两种分页

### 2.1 索引结构

```text
idx_events_created: (created_at DESC, id DESC)
  ↓
[2026-01-02T03:46:39Z|100000]
[2026-01-02T03:46:38Z|99999]
[2026-01-02T03:46:37Z|99998]
...
```

键本身就是「排序好的位置」，所以：

| 需求 | 能否直接利用 |
| --- | --- |
| `ORDER BY created_at DESC, id DESC` | 能（顺序一致）|
| `WHERE (created_at, id) < (?, ?)` | 能（行值比较 = 定位）|
| `OFFSET 99000` | 不能省（必须逐条数过去）|

### 2.2 行值比较

```sql
WHERE (created_at, id) < (?, ?)
```

等价于：

```sql
WHERE created_at < ?
   OR (created_at = ? AND id < ?)
```

但**行值比较能被索引当作一次定位**，写成 `OR` 形式则需要更复杂的计划。SQLite 3.15+ 支持行值比较。

### 2.3 执行计划判据（实测）

| 模式 | `detail` |
| --- | --- |
| `ORDER BY created_at DESC, id DESC` | `SCAN events USING INDEX idx_events_created` |
| `ORDER BY level`（无索引）| `SCAN events` + `USE TEMP B-TREE FOR ORDER BY` |

出现 `TEMP B-TREE` 就是**排序没走索引**，数据量一大就崩。

## 3. API 逐个拆解

### 3.1 偏移分页

```python
limit: int = Query(20, ge=1, le=100)
offset: int = Query(0, ge=0)
```

| 字段 | 作用 | 代价 |
| --- | --- | --- |
| `total` | 显示总条数 | 每次 `COUNT(*)`（实测 4.6ms）|
| `has_more` | 是否还有下一页 | `offset + len(items) < total` |

### 3.2 游标分页

```python
limit: int = Query(20, ge=1, le=100)
cursor: str | None = None
```

| 字段 | 作用 |
| --- | --- |
| `next_cursor` | 下一页起点，`None` 表示到底 |
| `has_more` | 多取 1 条判断，不查 `COUNT(*)` |

### 3.3 游标编码

```python
f"{created_at}|{event_id}"
```

**必须包含排序键的全部字段**。只放 `created_at` 时，同一时间戳的多条记录会被跳过或重复。

生产还应：base64（避免分隔符冲突）+ HMAC 签名（防篡改越权）+ 版本号（便于改排序）。

### 3.4 参数边界（实测）

| 输入 | 结果 |
| --- | --- |
| `limit=0` / `limit=101` | 422 |
| `offset=-1` | 422 |
| `cursor=not-a-cursor` | 400 `游标格式错误` |
| `cursor=<最小记录>` | 空页，`has_more=false` |

## 4. 边界条件

### 4.1 索引方向必须匹配（实测）

索引写成 `(created_at DESC, id DESC)` 才与 `ORDER BY ... DESC` 一致。
写成默认升序 `(created_at, id)` 时，SQLite 仍可反向扫描，但在分页 + 行值比较组合下容易出现 `TEMP B-TREE`。**规则**：索引方向照抄 `ORDER BY`。

### 4.2 `COUNT(*)` 的代价（实测）

10 万行 4.6ms。含义：

| 场景 | 影响 |
| --- | --- |
| 每页都 `COUNT(*)` | 每翻一页多 4.6ms |
| 1000 万行 | 单次约 400ms+ |

替代：

| 方案 | 说明 |
| --- | --- |
| 多取 1 条判断 `has_more` | 最省，但拿不到总数 |
| 缓存总数（Redis/内存 + TTL）| 略滞后 |
| 预估行数（`sqlite_stat1`）| 不准但 O(1) |
| 明确不提供总数 | 无限滚动场景常见 |

### 4.3 游标 vs 数据变化

| 变化 | 偏移分页 | 游标分页 |
| --- | --- | --- |
| 头部插入新数据 | 第 2 页重复第 1 页尾部 | 不重复 |
| 中间删除数据 | 漏行 | 不重复，可能跳过已删项 |
| 随机跳页 | 支持 | 不支持 |

### 4.4 索引失效的写法

| 写法 | 原因 |
| --- | --- |
| `WHERE date(created_at) = ?` | 函数包裹列 |
| `WHERE title LIKE '%x%'` | 前置通配 |
| `WHERE created_at + 0 > ?` | 表达式 |
| 类型不匹配（字符串 vs 数字）| 隐式转换 |

正确：

```sql
WHERE created_at >= ? AND created_at < ?
```

## 5. 注意事项与新手错误对照表

| 错误写法 / 操作 | 现象 | 正确写法 | 依据 |
| --- | --- | --- | --- |
| 深页用 `OFFSET` | 7ms 起，线性增长（实测）| 游标 | 实测 |
| 游标只放 `created_at` | 同时间戳跳/重 | `(created_at, id)` | 实测 |
| 索引方向与排序相反 | 出现 `TEMP B-TREE` | 索引写 `DESC` | 实测 |
| 索引缺唯一键 | 排序仍要临时表 | 复合索引 | 实测 |
| 每页 `COUNT(*)` | 每页多 4.6ms | 多取 1 条 / 缓存 | 实测 |
| `date(col) = ?` | 索引失效 | 范围查询 | `[P2]` |
| `LIKE '%x%'` | 全表扫 | 全文索引 | `[P2]` |
| 游标明文主键 | 可枚举 | base64 + 签名 | `[P3]` |
| 游标不带方向 | 反翻页错 | 带方向/版本 | `[P3]` |
| `limit` 无上限 | 一次拉全表 | `le=100` | 实测 |
| `offset` 允许负数 | 行为不定 | `ge=0` | 实测 |
| 非法游标不捕获 | 500 | 400 | 实测 |
| 分页同时返回 `total` 和游标 | 白付 `COUNT` | 二选一 | `[P1]` |
| 无限滚动用 offset | 重复/漏行 | 游标 | `[P1]` |
| 只测首页 | 深页问题漏测 | 测 `TOTAL-3` | 第 71 章 |
| 不验证执行计划 | 以为走索引 | `EXPLAIN` 断言 | 实测 |
| 造数据循环 `commit` | 灌库几分钟 | `executemany` 单事务 | 实测 |
| 用 `SELECT *` | 索引不覆盖、回表多 | 只选需要的列 | `[P2]` |
| 游标里放未加索引的字段 | 定位退化成全表扫 | 只放已建索引的排序键 | 实测 |

## 6. 最佳实践与编码建议

### 6.1 选型

| 场景 | 方案 |
| --- | --- |
| 后台管理表格（要页码/总数）| 偏移 + `COUNT(*)` 缓存 |
| 移动端无限滚动 | 游标 |
| 深页（> 1 万）| 游标，必须 |
| 导出全量 | 分批游标拉取，不用分页 API |

### 6.2 诊断流程

```text
1 慢？
   → EXPLAIN QUERY PLAN <sql>
2 出现 TEMP B-TREE？
   → 索引方向/字段不匹配
3 出现 SCAN 且无 INDEX？
   → 没有可用索引
4 走索引但仍慢？
   → 看 OFFSET：深页必然慢，换游标
5 单页仍慢？
   → 看是否回表太多（SELECT *）或 COUNT(*)
```

### 6.3 代码组织

| 位置 | 职责 |
| --- | --- |
| `db.py` | 建表、索引 |
| `repository.py` | 两条 SQL 常量集中 |
| `router.py` | 参数校验、游标编解码 |
| `verify.py` | 断言执行计划，不只断言结果 |

**关键**：把 SQL 提成模块常量（`OFFSET_SQL` / `KEYSET_SQL`），`EXPLAIN` 与业务查询用同一份，避免「测的和跑的不是一条」。
