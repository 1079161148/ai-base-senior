## 1. 概念：三件事不是一回事

| 手段 | 回答的问题 | 频率 |
| --- | --- | --- |
| 单元/接口测试（M12） | 这个函数/接口对不对 | 每次提交 |
| 验收（本章） | **这个服务能不能上线** | 每个里程碑 |
| 人工 review | 设计是否合理 | 每次 PR |

**验收的判据必须是可执行的**：能写进 `if` 的才叫验收，写不进的归 review。

## 2. 机制：七个维度的划分逻辑

| 维度 | 条数 | 防什么 | 漏了会怎样 |
| --- | --- | --- | --- |
| A 业务 | 20 | 功能缺失 | 用户点不出来 |
| B 错误契约 | 12 | 客户端分支崩塌 | 前端要写两套解析 |
| C 鉴权安全 | 15 | 越权/泄露 | 数据事故 |
| D 数据事务 | 10 | 脏数据 | 对账不平 |
| E 可观测 | 8 | 线上盲飞 | 故障定位 4 小时 |
| F 配置部署 | 8 | 换环境就崩 | 上线即回滚 |
| G 文档卫生 | 6 | 契约失真/隐患 | 半年后没人敢改 |

### 2.1 为什么 A 类最多而 G 类最少

| 维度 | 编写成本 | 出错概率 |
| --- | --- | --- |
| 业务 | 低（照契约写） | 中 |
| 安全 | 中 | **高** |
| 卫生 | 低（正则） | **高但易被忽略** |

条数分配不是按重要性，而是按**可断言点的密度**。安全类每条都很关键，但可断言点少（写/读/错令牌/默认令牌……）。

## 3. API 逐个拆解

### 3.1 跨章引用（实测）

```python
PROJECT = HERE.parent.parent / "78-生产化改造" / "examples"
sys.path.insert(0, str(PROJECT))
```

| 好处 | 代价 |
| --- | --- |
| 改 78 立刻反映 | 依赖目录结构 |
| 不重复代码 | 78 与 79 必须同仓库 |
| 验收的是真产物 | 相对路径要算准 |

**不这么做**的后果：79 章验收的是「79 章自己复制的代码」，78 章怎么改都能过 —— 验收失去意义。

### 3.2 环境变量时序（实测）

```text
先 os.environ[...] = ...
再 import main          ← main 顶层执行 settings = get_settings()
```

顺序反了，`main.settings` 就是旧值。这是本章最容易踩的坑之一。

### 3.3 断言粒度

| 粒度 | 问题 |
| --- | --- |
| 断整个 body | 加字段就红 |
| 断关键键 | ✅ 本章做法 |
| 断状态码 | 太弱，200 也可能是错误体 |

实测 B03 断的是 `set(payload) == {"error"}` —— 键集合，不管 `message` 文案。

### 3.4 性能烟测（实测）

```text
100 次 GET /api/v1/todos → P95 4.76ms / 总 366ms
```

| 指标 | 用途 |
| --- | --- |
| 总耗时 | 粗看是否退化 |
| P95 | 长尾（平均会掩盖） |
| 单次上限 | 发现偶发慢查询 |

**注意**：`TestClient` 走内存 ASGI，不含网络与真实 IO，**不能当压测**，只能当「有没有明显退化」的回归信号。

## 4. 边界条件

### 4.1 脚本验不了什么

| 项 | 为什么 |
| --- | --- |
| 设计是否合理 | 无客观判据 |
| 命名/可读性 | 主观 |
| 真实并发下的竞态 | `TestClient` 非真实并发 |
| 数据库索引是否缺 | 需执行计划 |
| 依赖库 CVE | 需专业扫描器 |
| 容量规划 | 需真实压测 |

这些归 review 与专门工具，**不要假装脚本覆盖了**。

### 4.2 临时库清理

```python
finally:
    shutil.rmtree(TMP_DIR, ignore_errors=True)
```

即使中途断言失败也要删。用 `ignore_errors=True` 避免清理本身抛错掩盖真因。

### 4.3 扫描自己

G 类扫描 `PROJECT.glob("*.py")` 时，若把 `verify.py` 也纳入，会因为脚本里含 `print`/`except` 而永远红。实测第一次就踩了：`['verify.py']`。

**修法**：`source_files()` 排除验收与测试脚本。

### 4.4 `204` 与响应声明

G06 最初只认 `200`/`201`，`DELETE` 的 `204` 被判失败。修法：`{"200","201","204"} & set(responses)`。

这类「断言本身写错」是验收脚本最常见的失败源——**先怀疑断言，再怀疑代码**。

## 5. 注意事项与新手错误对照表

| 错误写法 / 操作 | 现象 | 正确写法 | 依据 |
| --- | --- | --- | --- |
| 复制业务代码再验收 | 两边不同步 | `sys.path` 指向 | 实测 |
| env 在 import 后设 | 配置旧值 | import 前设 | 实测 |
| 扫描含 `verify.py` | G 类永红 | 排除脚本 | 实测 |
| 只验 happy path | 79 条全 200 | 每维度含反面 | 实测 |
| 断响应全文 | 加字段就红 | 断键集合 | 实测 |
| 不测 500 | 泄露无感知 | 强制异常端点 | 实测 |
| 只看平均耗时 | 长尾被掩盖 | 看 P95 | 实测 |
| 安全靠 review | 漏一处上线 | 脚本化 | 实测 |
| 用例共享数据 | 互相污染 | 每条前 `reset_db` | 实测 |
| 断日志总条数 | 加日志就红 | 断「有没有」 | 实测 |
| `204` 当失败 | G06 误报 | 允许 200/201/204 | 实测 |
| 跨章路径写死 | 换目录崩 | 相对 `HERE` | 实测 |
| 临时库不清理 | 磁盘残留 | `rmtree` | 实测 |
| 只跑一次 | 无回归 | 纳入 CI | `[c3]` |
| `TestClient` 当压测 | 结论失真 | 用真实压测工具 | 实测 |
| 断言 `message` 全文 | 改文案就红 | 断 `code` | 实测 |
| 忘记权威令牌失效用例 | 生产令牌泄露不知 | 显式测默认值 | 实测 |
| 验收与测试混在一个文件 | 职责不清 | `verify.py` vs `tests/` | 实测 |
| 断言依赖固定的自增 id | 换个种子就红 | 用响应里返回的 id | 实测 |

### 6.2 命名规范

| 前缀 | 含义 |
| --- | --- |
| `A01`–`A20` | 业务 |
| `B01`–`B12` | 错误契约 |
| `C01`–`C15` | 鉴权安全 |
| `D01`–`D10` | 数据事务 |
| `E01`–`E08` | 可观测 |
| `F01`–`F08` | 配置部署 |
| `G01`–`G06` | 文档卫生 |

编号即优先级：A 全绿只是「能用」，C/D 全绿才「敢上线」。

### 6.3 接入 CI

```yaml
# 伪代码
- run: uv run python verify.py     # 79 条，退出码非 0 即失败
- run: uv run pytest -q            # 接口用例
```

| 阶段 | 跑什么 |
| --- | --- |
| 每次提交 | `pytest` + `G` 类静态扫描 |
| 每次合并 | 全部 79 条 |
| 发布前 | 79 条 + 真实压测 + 依赖扫描 |

### 6.4 复盘产出的三个结论

| 结论 | 本章情况 |
| --- | --- |
| 哪类最容易错 | 断言本身写错（G06/`204`）、扫描范围（含 `verify.py`） |
| 哪类最值钱 | C 类（鉴权安全）与 D 类（事务） |
| 哪类最难自动化 | 设计合理性、命名、容量规划 |
