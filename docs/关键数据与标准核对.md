### 1.2 这条数据真正说明什么

**不是"Text-to-SQL 不能用了"，而是三件更精确的事：**

| 事实 | 含义 |
|------|------|
| **40.08% → 83.40%，三年涨 43 个点** | 这是**进步最快的领域之一**，不是"做不到" |
| **人类仍领先 9.6 个点（92.96 vs 83.40）** | 差距从 52 点缩到 9.6 点，**但没消失** |
| **R-VES 上机器已反超人类（84.10 vs 83.26）** | **机器写的 SQL 更高效**——因为它不受"人习惯写法"限制 |

> **修正后的判断**：
> **不做 Text-to-SQL 的理由，不再是"准确率太低"，而是"你无法承受那 17% 的错"。**

### 1.3 最关键的一条：所有 Top 成绩都带 Oracle Knowledge

> 榜单上**所有 Top 条目均标注 `Oracle Knowledge ✔️`** —— 即**提供了外部知识证据**，非"纯 schema"设置。

**这条直接验证了原文第 2.4 节的论断**：

> **"光给 DDL 是不够的——它必须看到真实的数据长什么样。"**

**官方榜单的实证**：

```
纯 schema 设置  →  成绩显著更低
+ Oracle Knowledge（外部证据/值说明）  →  才能进入 80+
```

> **所以"schema linking + 值采样"不是可选项，是拿分的必要条件。**

### 1.4 还有一组数字值得看：Mini-Dev 的经验上界

| 项 | 值 |
|----|-----|
| Mini-Dev 榜首（GPT-6.1 Sol） | **87.27**（SQLite 88.00 / MySQL 84.80 / PostgreSQL 89.00） |

## 三、SLO 数值："必须自定"是官方立场

### 3.1 Google SRE 的两句原文

> **"Our experience has shown that 100% reliability is the wrong target."**
> ——《Implementing SLOs》，Google SRE Workbook

> **"Start by thinking about (or finding out!) what your users care about, not what you can measure."**
> ——《Service Level Objectives》，Google SRE Book

**第一句的含义**：

> 即使有冗余组件、健康检查、快速故障转移，**仍存在多个组件同时失败的非零概率**。
> **而且即使你能做到 100%，用户的下游依赖也不允许。**

**第二句的含义**：

> **从"用户在意什么"出发，而不是从"你能测什么"出发。**
> 作者明确说：如果从"容易测的"开始，**会得到没用的 SLO**。

### 3.2 所以"数值为示例"不是免责声明，而是方法论

| 做法 | 评价 |
|------|------|
| 照抄别人的 SLO 数字 | ❌ **违反官方方法论** |
| 从用户在意的事倒推 | ✅ 官方路径 |
| 把 SLO 定成 100% | ❌ **官方明确说这是错的** |

### 3.3 官方的三段式链条

```
SLI（指标：你测什么）
  → SLO（目标：这个指标要到多少）
    → Error Budget（1 − SLO：可以花掉的失败额度）
      → 决策规则（预算还剩多少 → 能不能发版）
```

> **Google Cloud 的 SLO API 文档同样把这三步作为核心概念**：
> 选 SLI → 用 SLI 设 SLO → **用 SLO 隐含的错误预算来管理风险**。

### 3.4 对两个具体指标的重新表述

| 原表述 | 应改为 |
|--------|--------|
| "SLO 全部数值为示例" | **"数值必须从用户在意的事倒推；Google SRE 明确反对 100% 目标，也反对从易测指标出发"** |
| 告警分级 P0/P1/P2/P3 | 可保留，但应说明**分级应与错误预算消耗速度挂钩**（预算烧得快 = 高优先级） |

## 四、GDPR Art.17 与"模型能否遗忘"

### 4.1 条文结构（比我原来写的更完整）

**第 1 款：六个删除事由**（满足任一即须删除）

| # | 事由 |
|---|------|
| (a) | 数据对收集/处理目的**已不再必要** |
| (b) | 撤回同意且无其他法律依据 |
| (c) | **依第 21 条反对**且无优先正当理由（或反对直接营销） |
| (d) | **数据被非法处理** |
| (e) | 为遵守法律义务必须删除 |
| (f) | 依第 8(1) 条收集的儿童数据 |

**第 2 款：传播性删除义务（最容易被忽略）**

> 若控制者**已公开**数据：须考虑现有技术与实施成本，采取**合理步骤（包括技术措施）**，**通知其他正在处理该数据的控制者**——数据主体已请求删除任何指向、复制或复现该数据的链接或副本。

> **这一条在多 Agent / 多供应商架构下极其关键**：
> **删了自己的库不够，还要通知下游**。

**第 3 款：五类例外**

| 例外 | 内容 |
|------|------|
| 言论与信息自由 | 行使该权利 |
| 法律义务 / 公共任务 | 遵守法定义务、执行公共利益任务 |
| 公共卫生公共利益 | 依 9(2)(h)(i)、9(3) |
| 存档 / 科研 / 统计 | 依 89(1)，且删除会使目标无法实现或严重受损 |
| 法律主张 | 为确立、行使或抗辩法律主张 |

### 4.2 关键纠正：法条对"模型参数"是空白的

> **Art.17 原文并未规定"模型参数是否需删除""已训练模型如何处理"——这是当前法律实践中的开放争议点。**

**所以我原来那句"进了权重就删不掉"需要精确化**：

| 层次 | 准确表述 |
|------|----------|
| **技术事实** | ✅ 微调后的权重**无法定位并删除"某个样本的贡献"** |
| **法律义务** | ❓ **法条未明确**，属开放争议，**不能断言"违法"或"合规"** |
| **工程应对** | ✅ **训练前就决定"哪些数据不进训练集"**，这是唯一确定能做的 |

> **修正后的写法**：
> **"这不是技术难题，是架构选择"仍然成立，但理由要改成——"因为在法条明确之前，你无法用技术手段证明已删除"。**

### 4.3 对原文第五章的具体影响

原文的"三条防线"（训练前过滤 / 可追溯 / 可重建）**依然有效**，但应补充：

| 补充 | 理由 |
|------|------|
| **下游通知机制** | Art.17(2) 要求的传播性删除 |
| **反对权通道** | Art.17(1)(c) 援引 Art.21，需有明确的反对入口 |
| **例外情形记录** | 若主张"法律义务"或"法律主张"例外，需能举证 |

> ⚠️ **本文仍不是法律意见。** 条文摘录来自 `gdpr-info.eu`（条文汇编站，非官方发布页），**正式文本以 EUR-Lex 为准**。

## 五、成本收入比：有来源，但是二手

### 5.1 查到的数字

| 指标 | 数值 | 来源 |
|------|------|------|
| 传统 SaaS 毛利率 | **75–85%** | 多家 2026 年 benchmark 一致 |

| **推理成本占 AI 收入** | **约 23%** | 同上（"每 $1M AI 收入约 $230k 是推理成本"） |
| 早期/用高价模型的 AI SaaS | 50–65% | 二手 benchmark |

### 5.2 这解释了原文那个"< 30%"是怎么来的

```
ICONIQ：推理成本 ≈ 23% 收入
       → 毛利率 ≈ 52%（含基础设施、支持等全部 COGS）

如果把目标设成"推理成本 < 30% 收入"
       → 相当于毛利率 > 70%
       → 高于 AI 原生平均（52%），接近传统 SaaS 水平
```

**结论**：

> **"成本收入比 < 30%"不是一个虚构数字，它对应"高于 AI 行业平均的毛利要求"。**
> 但**必须标注**：这是**比行业平均更严的自我要求**，不是行业标准。

### 5.3 二手引用的局限（必须标注）

> ⚠️ **我未直读 ICONIQ 原始报告**，只看到多家独立来源（SaaS Mag、ProfitPathLogic、AI Cost Hub 等）**一致引用**同一组数字。
> 一致性提高了可信度，但**无法排除同源错误**。引用前建议找到 ICONIQ 原始发布。

### 5.4 "免费用户严格配额更赚钱"：删掉

> **查不到任何权威依据。** 这是产品直觉，不是可引用结论。

**建议替换为可验证的表述**：

## 六、HNSW / IVFFlat：有厂商官方默认值

### 6.1 最重要的一条：官方建议"先别动"

> **pgvector 官方 README 原文要点**：**"除非召回率低，否则使用默认值。"**
> 理由：`m` 和 `ef_construction` 会**显著影响构建时间**。

> **这直接推翻了我原文里"`efConstruction` 建议 100–200"的写法**——
> 那是社区习惯，**而官方默认只有 64，且官方建议先别调**。

### 6.2 官方默认值（pgvector v0.8.x）

| 参数 | **官方默认** | 含义 |
|------|-------------|------|
| `m` | **16** | 每层最大连接数 |
| `ef_construction` | **64** | 建图时的候选列表大小 |
| `hnsw.ef_search` | **40** | 查询时候选列表大小 |
| `hnsw.iterative_scan` | **默认未启用** | 过滤查询时扫描更多（`strict_order` / `relaxed_order`） |
| `hnsw.max_scan_tuples` | **20,000** | 迭代扫描最多访问元组数 |
| `hnsw.scan_mem_multiplier` | **1** | 扫描内存 = `work_mem` × 该值 |

> **对比我原文写的"`M` 16–64、`efConstruction` 100–200"**：
> **`m` 16–64 尚可（32/64 是常见调法），但 `ef_construction` 100–200 是加重不是标准**。

### 6.3 最有价值的官方证据：那个"10% 过滤只剩 4 行"

> **pgvector 官方原文**：
> **默认 `ef_search = 40` 时，若过滤条件只匹配 10% 的行，平均可能只有约 4 行结果。**

**这句话的价值**：

> **它把我原文里"多租户 post-filter 会导致返回空"从"经验判断"升级成了"官方量化的必然结果"。**

`40 × 10% = 4` —— **这是可以算出来的，不需要实测**。

### 6.4 官方的四种解法（按推荐顺序）

| 解法 | 说明 |
|------|------|
| **① 分区 / 分表** | **官方明确建议多租户场景按租户分区或分表**，避免互相影响召回与速度 |
| **② Partial index** | 部分索引（过滤条件固定的场景） |
| **③ `hnsw.iterative_scan`** | 匹配比例**高**时启用 |
| **④ 精确索引（B-tree）** | 匹配比例**低**时，精确索引往往更合适 |

> **原文只写了"pre-filter / oversample / 分区索引"，应补上官方提供的 `iterative_scan` 与"匹配比例低时干脆别用 ANN"。**

### 6.5 IVFFlat 的官方公式（比我原文的"经验值"更硬）

| 参数 | 官方规则 |
|------|----------|
| `lists` | **≤100 万行：`rows / 1000`**；**>100 万行：`sqrt(rows)`** |
| `ivfflat.probes` | 默认 **1**；**起始值用 `sqrt(lists)`** |
| 建索引时机 | **表里已有数据后再建**（IVFFlat 需要 k-means 训练，空表建索引效果差） |

**官方三条建议（原文列出）**：

1. 表里**已有数据**后再建索引
2. 选择合适的 `lists`
3. 查询时设置合适的 `probes`（起始 `sqrt(lists)`）

> **补充对比**：IVFFlat 构建更快、内存更少，但**查询性能（速度-召回权衡）通常不如 HNSW**。

### 6.6 HNSW 原论文到底说了什么

> **arXiv:1603.09320 摘要页确认的内容**：
> - 元素出现在最高层的概率由**指数衰减分布**随机选择，形成层级
> - **邻居选择启发式**在高召回和聚类数据上提升明显
> - 上层起始搜索 + 尺度分离 → **对数复杂度**（logarithmic complexity scaling）
> - 显著优于此前的开源 SOTA 纯向量方法

> **摘要页没有的内容**：`M` / `efConstruction` / `efSearch` 的定义原文、参数扫描实验、推荐取值。

> **所以**：**参数"论文推荐值"确实不存在**——我原来的标注是对的。
> **但"厂商官方默认值"存在**，这比"社区经验值"更值得引用。

### 7.2 四个核心功能

| 功能 | 定义 | 核心作用 |
|------|------|----------|
| **GOVERN** | 建立并维持 AI 风险管理的组织文化、政策、流程、职责与问责 | **贯穿并支撑其余三项**，是横向使能层 |
| **MAP** | 明确使用场景、利益相关方、预期目标与潜在影响，框定风险上下文 | 回答"在什么情境下、对谁、可能产生什么风险" |
| **MEASURE** | 用定量/定性方法分析、评估、监测、追踪已识别风险 | 回答"风险多大、如何验证、是否可接受" |
| **MANAGE** | 对风险排优先级，制定并执行响应、缓解、沟通、监控 | 回答"如何处置、谁负责、如何持续跟踪" |

### 7.3 三者关系（这是最容易画错的）

```
        ┌─────────── GOVERN（横向贯穿）───────────┐
        │                                          │
        ▼                                          ▼
      MAP ──────→ MEASURE ──────→ MANAGE
        ▲                          │
        └────── 结果反馈回 MAP ─────┘
```

| 要点 | 说明 |
|------|------|
| **GOVERN 不是循环里的一步** | 它是**跨领域的使能功能** |
| **MAP → MEASURE → MANAGE 是迭代循环** | **不是一次性线性流程** |
| **结果反馈回 MAP** | 随系统、场景、风险环境变化持续更新 |
| **与 GOVERN 双向反馈** | 治理决定管理方式，管理结果反过来调整治理 |

### 7.4 两个必须写清的定位

| 定位 | 说明 |
|------|------|
| **自愿性（voluntary）** | 官方明确 "intended for voluntary use"，**不是强制性法规** |
| **非行业特定（cross-sectoral）** | 面向所有行业，具体行业**需自行裁剪**落地 |

> **所以在 `Agent运营与治理.md` 里引用 AI RMF 时，不能写成"合规要求"，
> 只能写成"自愿性风险管理框架，可作为治理结构的参考骨架"。**

### 7.5 对 Agent 运营的具体映射（RMF → 本库章节）
