# 大模型会话（Conversation）最佳实践

## 结论

模型本身**无状态**，所谓"会话"完全由应用侧维护——每次请求都要把**完整历史消息**重新发一遍。因此会话管理的两条铁律是：

1. **历史上下文不可修改**（append-only），否则打不中 prompt cache，成本和延迟双升；
2. **不丢失推理上下文**，否则多轮推理链断裂，回复质量下降。

> 但第 2 条**厂商相关**：不同模型对"思维链是否回传"的要求相反，必须按厂商文档执行，不能一概而论（详见第三节）。

## 一、会话的本质

```
用户提问
   │
   ▼
应用侧拼接完整 messages 数组 ──▶ 发给模型（无状态）
   │                              │
   │                              ▼
   │                         返回 assistant 消息（由 AI 模型生成并返回给你的那条回复）
   ▼                              │
把 assistant 消息追加进历史 ◀──────┘
   │
   ▼
下一轮重复
```

关键认知：

| 事实 | 含义 |
|------|------|
| 模型不记住上一次请求 | 历史必须**每次全量发送** |
| 上下文 = 累积的消息列表 | 会话越长，token 越多、越贵 |
| 模型只"看到"你发过去的内容 | 本地删掉 ≠ 模型忘了，下次不带才会忘 |

## 二、铁律一：历史上下文不可修改

### 2.1 为什么不能改

Prompt Cache（提示词缓存）的核心机制是 **前缀匹配**：

- 服务商会缓存"与上次请求**逐字节完全一致的最长前缀**"的计算结果
- 只要历史消息有一个字不同，**从该位置往后全部缓存失效**
- 缓存命中时，这部分 token 按折扣价计费，且跳过计算 → **更便宜、更快**

因此对历史消息做任何"优化"都是负收益：

| 操作 | 后果 |
|------|------|
| 改写、润色历史消息 | 缓存全失效 |
| 删除中间某条消息 | 缓存全失效 |
| 调整消息顺序 | 缓存全失效 |
| 重新序列化导致空白/编码变化 | 缓存失效（隐蔽且常见） |

### 2.2 正确做法

- **只追加，不改写**（append-only）
- 历史消息**原样保存**，不做文本清洗、翻译、格式化
- **动态内容不要放在前缀**：时间戳、随机 ID、请求序号放在最后的 user 消息里，别塞进 system prompt
- 序列化方式固定：同一个字段顺序、同样的 JSON 编码，避免"内容相同但字节不同"

### 2.3 需要裁剪时怎么办

上下文终会超长，无法永远 append。此时：

- **从最旧处裁**（保留 system + 最近 N 轮），让前缀尽可能长地保持一致
- 一旦裁剪，该会话的缓存**必然失效**，应接受这一成本，而非为省缓存牺牲正确性
- 更好的做法：**新开会话 + 携带摘要**，而不是破坏老会话的历史

### 2.4 各厂商缓存机制对比

| 厂商 | 缓存方式 | 匹配粒度 | 备注 |
|------|----------|----------|------|
| **OpenAI** | 自动启用（提示较长时） | 最长公共前缀 | 无需显式标记 |
| **Anthropic** | 显式 `cache_control` 断点 | 到断点为止的前缀 | 有 TTL，需按文档设置 |
| **Google Gemini** | 显式 context caching | 前缀 | 需主动创建缓存 |

> 无论哪家，**前缀越稳定、越靠前，命中率越高**。

## 三、铁律二：保留推理上下文（需区分厂商）

### 3.1 为什么推理上下文重要

对具备"思维链 / reasoning"能力的模型，推理过程是**多轮任务的中间工作记忆**：

- 丢掉它，模型下一轮要**重新推理**一遍 → 慢且可能得出不同结论
- 复杂任务（多步计算、工具调用）中，推理链断裂会直接导致结果不一致
- 尤其在 **工具调用** 场景：模型"想清楚要调什么工具"的过程若丢失，后续无法衔接

### 3.2 厂商差异（关键，别一概而论）

不同模型对 reasoning 的**返回方式**和**是否应回传**规定不同：

| 模型 / 厂商 | reasoning 是否透出 | 多轮是否回传 | 依据 |
|-------------|--------------------|--------------|------|
| **Anthropic（extended thinking）** | 返回 `thinking` 块（带签名） | **工具调用场景必须回传**，否则报错或丢失连续性 | 官方文档 |
| **DeepSeek（R1 等）** | 单独 `reasoning_content` 字段 | **官方建议不要回传**，只回传 `content` | 官方文档 |
| **OpenAI（o 系列等）** | 默认**不暴露**原始推理 | 无需处理 | 由平台内部管理 |
| **其它开源推理模型** | 取决于模板与推理框架 | 按模型 README | — |

> 结论：**"保留思维链"不是普适铁律**。正确姿态是——**遵循你所调用模型的官方约定，不擅自删改，也不盲目塞回**。

### 3.3 实际操作建议

- 如果框架/厂商要求回传 reasoning 块：**原样回传**，不要编辑签名、不要裁剪内容
- 如果厂商明确说不回传：**只传最终 content**，把推理内容仅用于日志/调试
- 自己实现推理时：把 reasoning 与最终答案**分开存储**，便于按厂商规则灵活处理

## 四、消息结构规范

| 规范 | 说明 |
|------|------|
| **role 合法** | 只用厂商支持的 role（system / user / assistant / tool / developer） |
| **tool 调用必须配对** | `assistant.tool_calls` 与后续 `tool` 结果消息必须成对出现，不能只留其一 |
| **顺序不可乱** | tool 结果必须紧跟对应的 tool_call |
| **content 类型一致** | 文本 vs 多模态内容块，按厂商 schema 传 |
| **不要重复 system** | 一般只在开头放一次（各厂商规则略有差异） |

## 五、上下文窗口管理

会话无限增长必然撞上窗口上限（详见 `Transformer 推理机制.md` 中的上下文窗口）。处理策略：

| 策略 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **滑动窗口** | 只保留最近 N 轮 | 简单、缓存命中好（前缀不变） | 丢失早期信息 |
| **摘要压缩** | 把早期对话总结成一段 | 保留语义 | **破坏缓存前缀**、有信息损失 |
| **外置检索（RAG）** | 历史存库，按需检索注入 | 支持超长历史 | 增加检索链路与延迟 |

**取舍核心**：摘要压缩质量高但会**让缓存失效**；滑动窗口缓存友好但会失忆。没有银弹，按业务选。

## 六、多轮工具调用

- `assistant` 的 `tool_calls` 与 `tool` 结果**必须成对**
- 中间的工具结果**不能删**——它和推理链一样属于上下文
- 并行工具调用时，结果的 `tool_call_id` 必须与请求一一对应
- 工具报错也要作为结果回传，让模型知道发生了什么，而不是静默丢弃

## 七、持久化与会话隔离

| 关注点 | 实践 |
|--------|------|
| **会话 ID** | 每段对话有唯一 ID，消息带序号 |
| **存储** | 落库（消息表 + 会话表），支持断点续聊 |
| **并发** | 同一会话并发写入需加锁/串行化，避免消息乱序 |
| **用户隔离** | 严格按用户/租户隔离，防止串号泄露 |
| **审计** | 记录每次请求的 token 用量、模型版本、耗时 |

## 八、常见反模式

| 反模式 | 问题 | 后果 |
|--------|------|------|
| 每次请求动态改 system prompt | 前缀每次都不同 | 缓存 0 命中，成本翻倍 |
| 在历史消息里做"文本清洗" | 改变了已发送内容 | 缓存失效 |
| 把时间戳/随机 ID 放 system | 前缀不稳定 | 缓存失效 |
| 删掉中间 tool 结果 | 调用链断裂 | 模型行为异常 |
| 无脑丢弃 reasoning（该保留时） | 推理断裂 | 质量下降、结论不一致 |
| 无脑回传 reasoning（该丢弃时） | 违反厂商约定 | 报错或浪费 token |
| 上下文无限塞 | 超窗口 | 被硬截断，关键信息丢失 |
| 会话不隔离 | 串号 | 隐私事故 |

## 九、Checklist

**缓存友好**
- [ ] system prompt 固定不变，且放在最前
- [ ] 历史消息 append-only，从不改写
- [ ] 动态内容（时间、ID）只放最后一轮
- [ ] 序列化方式稳定（字段顺序、编码一致）

**推理连续性**
- [ ] 已确认当前模型的 reasoning 回传规则
- [ ] 需要回传时原样保留（含签名）
- [ ] 不需要回传时不塞回去

**结构与安全**
- [ ] tool_calls 与 tool 结果成对
- [ ] 上下文超限时有明确裁剪策略
- [ ] 会话按用户隔离、有持久化与审计

## 十、总结

会话管理的本质是**在"省钱快"和"记得清"之间做工程权衡**：

- **不改历史** → 保住 prompt cache → 省钱、提速
- **管理好推理上下文** → 保住多轮质量 → 答得准

而这两条能否成立，前提都是**先搞清楚你所调用模型的官方约定**——缓存怎么匹配、reasoning 怎么回传，各厂商规则不同，照搬别家的做法往往适得其反。
