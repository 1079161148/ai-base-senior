# Agent 成本优化

> **权威依据**
> ① **Anthropic** Prompt Caching 官方文档 — 计价倍率与命中条件
> ② **Anthropic**《How we built our multi-agent research system》— 4× / 15× token 实测
> ③ **Anthropic**《Contextual Retrieval》— 缓存带来的降本数据
> ④ OpenAI / Anthropic / Google Batch API — 50% 折扣、24 小时窗口
> ⑤ 本知识库：`Token统计.md`、`Context Engineering.md`、`大模型会话最佳实践.md`

## 结论

**成本 = 输入 token × 输入单价 + 输出 token × 输出单价**

**三个杠杆，按 ROI 排序：**

| # | 杠杆 | 典型收益 | 难度 |
|---|------|----------|------|
| **1** | **Prompt Caching（前缀缓存）** | **输入成本降到 1/10** | 中（有工程约束） |
| **2** | **减少 token 本身** | 30%–70% | 中 |
| **3** | **模型分层 / 路由** | 50%–90% | 中 |
| **4** | **Batch API** | **固定 50%** | 低（但要能等 24h） |
| **5** | **架构级（确定性代码替代 LLM）** | 可能 100% | 高 |

> **最重要的一句**：**缓存不是"打开开关就省钱"，它是一种"必须被设计的架构约束"。**
> 前缀不稳定，缓存命中率就是 0——**你付了写入溢价却拿不到读取折扣**。

## 一、先把账算清楚

### 1.1 Agent 的成本结构与聊天机器人完全不同

> **Anthropic 的实测数据**（相对普通 chat 交互的 token 消耗）：

| 形态 | token 倍数 |
|------|-----------|
| 普通 chat | 1× |
| **单 Agent（工具循环）** | **约 4×** |
| **多 Agent** | **约 15×** |

**为什么涨这么快**：

| 原因 | 说明 |
|------|------|
| **多轮叠加** | 每轮都把历史全部重发一遍 |
| **工具定义常驻** | 每次请求都带全部工具的 JSON Schema |
| **上下文累积** | 第 10 轮的输入 = 前 9 轮的全部内容 |
| **重试与循环** | 失败了要重来 |
| **子代理** | 每个独立上下文都要重新"热身" |

### 1.2 一个具体的算例

```
单轮 chat：    输入 2k   + 输出 500    = 2.5k token
单 Agent 8 轮：输入 60k  + 输出 4k     = 64k token   ← 25 倍
```

> **这就是为什么"做个 Agent"和"做个聊天"的成本不是一个量级。**

### 1.3 输入和输出不对称

| | 典型倍率 |
|---|---|
| 输入单价 | 1× |
| **输出单价** | **3–5×** |

**推论**：

> **同样的 1000 token，写在输出里比写在输入里贵 3–5 倍。**
> 所以"让模型少说废话"往往比"少给模型资料"更省钱。

## 二、Agent 成本为什么容易失控

| 失控点 | 机制 | 后果 |
|--------|------|------|
| **工具太多** | 20 个工具的 Schema 轻松上万 token，**每轮都带** | "什么都没干就花了很多钱" |
| **上下文不清理** | 历史无限追加 | 第 N 轮成本 ∝ N |
| **工具结果全留** | 一次检索返回 50 个 chunk 全留在历史里 | 后续每一轮都在为它付费 |
| **循环** | 检测不到重复就无限重试 | 成本爆炸 |
| **重试无上限** | 失败就重试 | 雪崩 |
| **子代理泄漏** | 子代理产物把主上下文撑大 | 边际成本递增 |

> **一个反直觉的事实**：**Agent 的成本不是"每次调用贵"，而是"调用次数 × 每轮都在变大的输入"。**

## 三、杠杆一：Prompt Caching（最大杠杆）

### 3.1 计价倍率（Anthropic 官方）

以基础输入单价为 1× 基准：

| 项目 | 倍率 |
|------|------|
| **5 分钟缓存写入** | **1.25×** |
| **1 小时缓存写入** | **2×** |
| **缓存命中 / 刷新** | **0.1×** |
| 输出 token | 1×（不受影响） |
| 缓存断点本身 | **不收费** |

**具体单价示例**（美元 / 百万 token）：

| 模型 | 基础输入 | 5m 写入 | 1h 写入 | **命中** |
|------|---------|---------|---------|---------|
| Opus 系列 | $15 | $18.75 | $30 | **$1.50** |
| Sonnet 4.5 系列 | $3 | $3.75 | $6 | **$0.30** |
| Haiku 4.5 | $1 | $1.25 | $2 | **$0.10** |

> **命中价是基础价的 1/10。** 这就是为什么值得为它改架构。

### 3.2 一个必须算清的账

```
场景：system prompt + 工具定义 = 20k token，每天调用 1000 次

不用缓存：
  20,000 × 1000 = 20M token/天  × $3/M = $60/天

用缓存（首次写入后全部命中）：
  写入：20,000 × $3.75/M         ≈ $0.075（一次性，5 分钟 TTL 内可能要多写几次）
  命中：20,000 × 999 × $0.30/M   ≈ $6/天

省了约 90%
```

> **但如果前缀不稳定，命中率是 0**：
> `20,000 × 1000 × $3.75/M ≈ $225/天`——**比不用缓存还贵 3.75 倍**。

> **⚠️ 这是最危险的陷阱：配错缓存 = 主动涨价。**

### 3.3 命中条件（必须全部满足）

| 条件 | 说明 |
|------|------|
| **① 前缀完全一致** | 包括所有文本与图像，**一个字符都不能变** |
| **② 层级顺序** | `tools` → `system` → `messages`，缓存的是**从开头到标记块的完整前缀** |
| **③ 累积哈希** | 每块依赖它前面**所有**内容——**前面改一个字符，后面全失效** |
| **④ 在 TTL 内** | 默认 5 分钟，**每次读取免费刷新**计时 |
| **⑤ 达到最小长度** | 见下表 |
| **⑥ 同组织内** | 不同组织之间**不共享缓存** |

### 3.4 最小可缓存长度（低于此值不缓存）

| 模型 | 最小 token |
|------|-----------|
| Opus 4.1 / Opus 4 / Sonnet 4.5 / Sonnet 4 / Sonnet 3.7 | **1024** |
| Haiku 4.5 | **4096** |
| Haiku 3.5 / Haiku 3 | **2048** |

> **含义**：**短 prompt 配缓存是白费**——标记了也不会缓存。

### 3.5 20 块回看窗口（最容易踩的坑）

> 系统从你的**显式断点向后逐块回溯，最多检查 20 块**。

| 场景 | 结果 |
|------|------|
| 30 个块，只在第 30 块设断点，改第 25 块 | ✅ 可回退命中第 24 块 |
| 30 个块，只在第 30 块设断点，改第 5 块 | ❌ **超出 20 块窗口，完全未命中** |
| 30 个块，在第 5 块前也设断点，改第 5 块 | ✅ 可命中第 4 块 |

> **推论**：**内容块很多时，断点不能只设在末尾。**
> 断点上限 **4 个**，要花在最值的地方。

### 3.6 怎么组织内容（最关键的一节）

**核心原则：静态前置，动态后置。**

```
┌─────────────────────────────────┐
│ ① 工具定义（几乎不变）           │ ← 断点 1
├─────────────────────────────────┤
│ ② System Prompt（很少变）        │ ← 断点 2
├─────────────────────────────────┤
│ ③ 背景资料 / few-shot（每天变）   │ ← 断点 3
├─────────────────────────────────┤
│ ④ 对话历史（每轮变）             │ ← 断点 4
├─────────────────────────────────┤
│ ⑤ 本轮用户问题（每次都变）        │ ← 不缓存
└─────────────────────────────────┘
```

**收益量化**：

> Anthropic 官方示例：首次调用 `188,086 写入 / 0 读取 / 21 输入`；二次调用变成 `0 写入 / 188,086 读取 / 21 输入`。
> **只有最后那 21 个 token 是新处理的。**

### 3.7 失效条件（改了就不命中）

| 变更内容 | 影响 tools 缓存 | 影响 system 缓存 |
|----------|----------------|-----------------|
| **工具定义（名称/描述/参数）** | ❌ 失效 | ❌ 失效 |
| 开/关 web search | ✅ 保留 | ❌ 失效 |
| 开/关 citations | ✅ 保留 | ❌ 失效 |
| 修改 `tool_choice` | ✅ 保留 | ✅ 保留 |
| **增删图像（任意位置）** | ✅ | ✅ |
| 扩展思考参数变更 | ✅ | ✅ |

**另一个隐蔽的失效原因（很真实）**：

> **`tool_use` 块里的 JSON key 顺序不稳定会破坏缓存。**
> 某些语言的序列化器（如 Swift、Go）会随机化 key 顺序 → **必须强制稳定排序**。

### 3.8 TTL 怎么选

| TTL | 适用 |
|-----|------|
| **5 分钟（默认）** | 连续对话、高频复用 |
| **1 小时（2× 写入价）** | 使用间隔 >5 分钟但 <1 小时、对延迟敏感 |

> **混用规则**：同一请求可以混用，但**长 TTL 必须排在短 TTL 之前**。

### 3.9 缓存对检索的额外价值

> **Anthropic Contextual Retrieval**：用 prompt caching 让"为每个 chunk 生成上下文"变得可行——**整篇文档缓存一次，后续每块引用缓存**，成本约 **$1.02 / 百万文档 token**。

**另一条**：知识库 < 200k tokens 时，**直接用缓存全量塞入**——"缓存可使延迟降低 >2×、成本降低至多 90%"。

## 四、杠杆二：减少 token 本身

### 4.1 五个手段（按效果排序）

| 手段 | 做法 | 典型收益 |
|------|------|----------|
| **① 清理历史工具结果** | 早已调用过的工具，Agent 何必再看原始输出？ | **最高** |
| **② 上下文压缩（Compaction）** | 接近上限时摘要已完成阶段 | 高 |
| **③ 精简工具集** | 每场景 ≤ 30 个工具；用子代理收窄工具面 | 高 |
| **④ 输出预算** | 明确"回答不超过 N 字" | 中 |
| **⑤ 子代理隔离** | 高产出操作放子代理，只回传摘要 | 中 |

### 4.2 为什么"清理工具结果"是最低垂的果实

```
第 1 轮：调用 search("A") → 返回 8k token 的原始结果
第 2 轮：调用 search("B") → 上下文 = 8k(旧) + 8k(新)
第 3 轮：调用 fetch(url)  → 上下文 = 16k + 15k(url 正文)
...
第 10 轮：上下文里塞满了前 9 轮再也不会用到的原始数据
```

**正确做法**：

```
第 1 轮后：search("A") 的结果 → 压缩成 "找到 3 篇相关文档：X/Y/Z（要点：...）"
```

> **Anthropic 明确把"清理历史工具结果"列为 Compaction 的"最低垂的果实"。**

### 4.3 输出侧的三个技巧

| 技巧 | 说明 |
|------|------|
| **明确长度约束** | "用不超过 100 字总结" |
| **结构化输出** | JSON 比散文更省（无寒暄、无重复） |
| **中间结果不输出** | 推理过程留在 thinking 里，别写进正文 |

### 4.4 工具集精简的量化

| 工具数 | 大致 Schema token |
|--------|------------------|
| 5 个 | ~2k |
| 20 个 | ~8k |
| 50 个 | ~20k |
| 100+ | 40k+ |

> 每轮都带 → **100 个工具 × 10 轮 = 400k token 的纯工具定义**。

**对策**：**用子代理收窄工具面**——不同子代理只带自己需要的工具。

## 五、杠杆三：模型分层与路由

### 5.1 三种策略

| 策略 | 做法 | 收益 | 风险 |
|------|------|------|------|
| **静态分层** | 简单任务固定用小模型 | 高 | 任务分类要准 |
| **级联（Cascade）** | 小模型先答，置信度低才升级大模型 | **很高** | 需要置信度判断 |
| **动态路由** | 按预估 token / 复杂度选模型 | 高 | 需要预估能力 |

### 5.2 级联的实现

```python
def cascade(prompt: str) -> str:
    # ① 先用便宜模型
    small = call(model="haiku", prompt=prompt, with_confidence=True)

    if small.confidence >= 0.85:
        return small.text

    # ② 置信度低 → 升级
    return call(model="sonnet", prompt=prompt).text
```

> **前提**：模型能给出可靠的置信度。**没有这个，级联会变成"两级都跑"，反而更贵。**

### 5.3 任务分层示例

| 任务 | 模型 |
|------|------|
| 分类、打标、格式转换 | 小模型（Haiku 级） |
| 检索后总结、单步推理 | 中模型 |
| 复杂规划、代码生成、多步推理 | 大模型 |
| **最终质量审查** | 大模型（**只在关键节点**） |

### 5.4 一个容易被忽略的降本点

> **Anthropic 实测**：升级到 Sonnet 4 带来的性能增益，**大于把 Sonnet 3.7 的 token 预算翻倍**。

**含义**：**"用更好的模型"有时比"用更多 token"更划算**——成本优化不等于"无脑用小模型"。

## 六、杠杆四：Batch API

### 6.1 核心条款（三家基本一致）

| 条款 | 内容 |
|------|------|
| **折扣** | **输入与输出均 50% off** |
| **返回窗口** | **最长 24 小时** |
| **形态** | 提交一个 job，拿 job id，之后取结果 |

> **最适合的场景**：离线评测、批量数据标注、历史文档处理、大规模 embedding。

### 6.2 什么时候用

| 场景 | 适合 |
|------|------|
| **跑评测集** | ✅ 完美（不需要实时） |
| **批量生成 embedding** | ✅ |
| **夜间批处理报告** | ✅ |
| **Agent 实时任务** | ❌ |

### 6.3 注意点

| 点 | 说明 |
|----|------|
| **失败请求的计费** | 各家规则不同，需核对 |
| **超时** | 24 小时内未完成可能部分失败 |
| **不适合 Agent 主循环** | Agent 需要即时反馈 |

## 七、杠杆五：架构级优化

### 7.1 五条原则

| # | 原则 | 收益 |
|---|------|------|
| **① 确定性代码替代 LLM** | "普通代码能可靠做出的决策，那个节点就不需要 Agent" | **可能 100%** |
| **② 并行代替串行** | 无依赖步骤并行，总时延降但 token 不变 | 省时间不省钱 |
| **③ 中间结果缓存** | 相同子查询直接复用 | 高 |
| **④ 提前终止** | 足够好就停，不要跑满 | 高 |
| **⑤ 输出写入文件系统** | 只把轻量引用回传主上下文 | 高 |

### 7.2 第 1 条最容易被忽视

```python
# ❌ 贵且不稳
category = llm(f"这段文本属于以下哪类：{CATEGORIES}\n\n{text}")

# ✅ 免费且确定
if "退款" in text or "退货" in text:
    category = "after_sales"
```

> **加一条规则，可能顶掉 30% 的 LLM 调用。**

### 7.3 第 5 条：文件系统当"外部内存"

> **Anthropic 的做法**：子 Agent 把结构化产物（代码、报告、可视化）**存到外部系统，只回传轻量引用**给协调者。
> 好处：避免多级传递中的失真与 **token 膨胀**。

## 八、成本监控与治理

### 8.1 必看的六个指标

| 指标 | 为什么 |
|------|--------|
| **单任务成本（cost per task）** | **唯一真正有意义的单位经济指标** |
| **缓存命中率** | 命中率低 = 前缀不稳定 = 白付写入溢价 |
| **输入/输出 token 比** | 比例异常说明上下文失控 |
| **工具定义占比** | 占比高说明工具太多 |
| **平均轮数** | 上升 = 效率下降 |
| **重试率** | 上升 = 不稳定 |

### 8.2 为什么要看"单任务成本"而不是"总成本"

```
总成本 = 请求数 × 单次成本

如果业务量翻倍，总成本翻倍是正常的。
但单任务成本上升，说明系统在变差。
```

> **只看总成本会让你得出错误结论。**

### 8.3 治理机制

| 机制 | 作用 |
|------|------|
| **单请求成本上限** | 防单次爆炸 |
| **用户/租户日预算** | 防滥用 |
| **异常用量告警** | 及时发现 |
| **成本归因**（按功能/用户/模型） | 知道钱花在哪 |
| **估算前置拦截** | 见 `Token统计.md` |

## 九、优化优先级（ROI 排序）

| 优先级 | 动作 | 工作量 | 收益 | 风险 |
|--------|------|--------|------|------|
| **1** | **配好 Prompt Caching** | 中 | **最高（10×）** | 配错会涨价 |
| **2** | **清理历史工具结果** | 低 | 高 | 低 |
| **3** | **精简工具集** | 中 | 高 | 可能降低能力 |
| **4** | **静态模型分层** | 低 | 高 | 质量问题 |
| **5** | **输出长度约束** | 低 | 中 | 低 |
| **6** | **离线任务走 Batch** | 低 | 固定 50% | 要能等 |
| **7** | **级联路由** | 高 | 很高 | **需要可靠置信度** |
| **8** | **确定性代码替代** | 高 | 可能 100% | 需逐点分析 |

> **先做 1–5，它们加起来能砍掉大部分成本，且风险低。**

## 十、常见误区

| 误区 | 事实 |
|------|------|
| **"开了缓存就一定省钱"** | ❌ 前缀不稳定时，**你付 1.25× 却拿不到 0.1×** |
| "成本主要看单价" | ❌ **看总量与结构**；小模型跑 10 倍轮数可能更贵 |
| "输出和输入一样贵" | ❌ 输出常贵 **3–5 倍** |
| "上下文窗口大就不用管成本" | ❌ 窗口大 = **能塞更多 = 更容易烧钱** |
| "用小模型总是更省" | ❌ 能力不足 → 重试 → **可能更贵** |
| "缓存是开关" | ❌ 是**架构约束**（前缀稳定、断点位置、20 块窗口） |
| "优化成本必然降质量" | ❌ 清理工具结果、确定性替代**同时提升质量与速度** |
| "看总成本就知道有没有优化" | ❌ 看**单任务成本** |
| "Batch 只适合离线" | ⚠️ 是的，但**评测与数据准备占的成本常被低估** |
| "多 Agent 更贵所以别用" | ⚠️ 15× 是事实，但**如果它把任务成功率从 40% 提到 90%，总成本反而更低** |

## 十一、Checklist

**先测量**
- [ ] 有**单任务成本**指标
- [ ] 有**缓存命中率**
- [ ] 有**输入/输出 token 比**
- [ ] 有**工具定义占比**
- [ ] 成本能按功能/用户/模型归因

**缓存**
- [ ] 静态内容全部前置（工具 → system → 资料 → 历史 → 本轮问题）
- [ ] 断点设在**分层的边界**
- [ ] 内容块 >20 时，断点**不只在末尾**

## 十二、总结

**一句话公式：**

```
成本 = (输入 token × 1 + 输出 token × 3~5) × 单价
       ↑ 用缓存打 1 折      ↑ 靠简短省
```

**五条最值得记住的原则**：

1. **缓存是最大的杠杆，但它必须被设计** —— 前缀不稳定就是白花钱
2. **Agent 的成本不是"单次贵"，是"轮数 × 变大的输入"**
3. **清理历史工具结果是最低垂的果实**
4. **看单任务成本，不看总成本**
5. **成本优化不等于用小模型** —— 更好的模型有时比更多 token 更划算

> **最后一句话**：
> **Agent 省钱的核心不在"砍功能"，而在"不重复付费"——**
> **同一段内容只该被处理一次，无论是靠缓存、靠压缩，还是靠干脆不发给模型。**
