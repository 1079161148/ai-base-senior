# Harness Engineering（驾驭工程）

> **权威依据**
> ① Mitchell Hashimoto《My AI Adoption Journey》，2026-02-05（术语提出者）
> ② OpenAI《Harness Engineering: Leveraging Codex in an Agent-First World》，2026-02-11

## 结论

**Harness Engineering 是"围绕 AI Agent 构建约束、上下文、验证与反馈系统"的工程学科——目标不是让模型更聪明，而是让模型稳定地、可复现地产出正确结果。**

它解决的核心问题是：

> **模型能力是通用品，可靠性的差距不在模型，而在你为它搭的那套"驾驭系统"。**

一句话记住：**同一匹马，换套马具，表现判若两人。**

## 一、术语来源

| 时间 | 事件 | 说明 |
|------|------|------|
| **2026-02-05** | Mitchell Hashimoto 发表《My AI Adoption Journey》 | 首次提出 **Engineer the Harness** |
| **2026-02-11** | OpenAI 发表《Harness Engineering》 | 采纳该词并系统化为组织级方法论 |

### 1.1 Mitchell Hashimoto 的原始定义

> **"每当发现 agent 犯错，就花时间工程化一个解决方案，使 agent 再也不会犯这个错。"**

（他的原文注明：不确定业界是否已有公认术语，若有会跟进采用。）

### 1.2 OpenAI 的系统化

OpenAI 用它描述一件更大的事：**一个 3 人（后扩到 7 人）团队，5 个月、约 100 万行代码、约 1500 个 PR、零手写代码**的产品开发方式。

> OpenAI 原文结论（意译）：**最棘手的挑战不再是写代码，而是设计环境、反馈回路和控制系统。**

### 1.3 词源隐喻：为什么是"马具"

**Harness 本义是马具**——缰绳、鞍具、嚼子，一整套用来驾驭强壮但不可预测的动物的装备。

| 隐喻 | 对应 |
|------|------|
| **马** | AI 模型：力量大、速度快，但自己不知道往哪跑 |
| **马具（harness）** | 基础设施：约束、护栏、反馈回路 |
| **骑手** | 人类工程师：给方向，不亲自跑 |

> 没有 harness 的 Coding Agent 就像草原上撒欢的纯血马——**跑得漂亮，但哪儿也到不了**。

## 二、Harness 由什么组成（四要素）

| 要素 | 回答什么 | 具体手段 |
|------|----------|----------|
| **① 约束（Constrain）** | Agent **能**做什么 | 架构边界、依赖规则、权限控制 |
| **② 告知（Inform）** | Agent **该**做什么 | 上下文工程、文档、AGENTS.md |
| **③ 验证（Verify）** | Agent 做**对**了没 | 测试、lint、类型检查、CI |
| **④ 纠正（Correct）** | 做错了**怎么办** | 反馈回路、自修复、自动回滚 |

> **四者缺一不可**：只有约束没有验证 → 不知道对不对；只有验证没有纠正 → 错了不会改。

## 三、三根支柱（OpenAI 的系统实践）

### 3.1 支柱一：上下文工程（Context）

**核心命题**：

> **从 Agent 视角看，运行时访问不到的东西就不存在。**
> Google Docs 的决策、Slack 的讨论、人脑中的共识——**全在它的视野之外**。**仓库里版本化的文件才是它的全部世界。**

#### 反面教训：巨型 AGENTS.md 会失败

| 失败原因 | 说明 |
|----------|------|
| **上下文稀缺** | 大文件挤占任务描述与代码的空间 |
| **重点消失** | 什么都标"重要" = 都不重要 |
| **迅速腐烂** | 过时规则堆积成"文件坟场" |

#### 最终方案

> **`AGENTS.md` 压缩到约 100 行，只作目录，指向 `docs/` 下的细分文档。**
> 原则：**给 Agent 一张地图，别给千页说明书。**

#### 动态上下文

| 手段 | 作用 |
|------|------|
| 按 **git worktree** 启动独立实例 | 隔离，避免互相污染 |
| 接入 **Chrome DevTools 协议** | 让 Agent 自己操作浏览器复现 bug |
| 每 worktree 部署**临时可观测性栈** | LogQL 查日志、PromQL 查指标 |

> 关键效果：**"服务启动在 800ms 内"这类要求，变成 Agent 可自主验证的指标**——它不需要问你，自己能查。

### 3.2 支柱二：架构约束（Architecture）

**核心策略**：**约束不变量，不管实现细节。**

#### 分层结构

```
Types → Config → Repo → Service → Runtime → UI
```

- 依赖方向**单向**
- 横切逻辑（认证、遥测、功能开关）统一走 `Providers` 接口

#### 强制执行

- 通过**自定义 linter 和结构测试**落地
- **linter 本身也由 Codex 生成**

#### 一个巧妙的细节

> **lint 报错信息里直接写修复指令**——Agent 看到报错的同时就拿到修改指南。

#### 理念：约束"什么必须做"，不约束"怎么做"

> 例：要求在数据边界做校验（"Parse, don't validate"），但**不指定库**——模型偏好 Zod 就用 Zod。

#### 为什么这对 Agent 尤为重要

> 这类治理通常是**几百人大团队才做**的事，对 Agent 反而是**早期前提**：
> **没有约束，速度越快漂移越严重。写一次，处处生效，具有乘数效应。**

### 3.3 支柱三：熵管理（Entropy）

**问题**：**Agent 会忠实复现仓库中已有的模式——包括不好的。**

命名惯例分歧、文档代码脱节、死代码堆积——熵增不可避免。

#### 失败的初期方案

> 每周五花 20% 时间手动清理"AI 残渣"→ 很快扛不住。

#### 替代方案：把"黄金原则"编码进仓库

用**后台 Codex 任务**定期：

1. 扫描偏差
2. 更新质量评分
3. 提重构 PR（**多数一分钟内审完自动合并**）

> 像**垃圾回收**一样，持续小额偿还技术债，而不是任其复利滚存。

#### 为什么这是最被低估的一环

> **没有熵管理的 harness 会随时间衰败**——Agent 开始复制更多坏模式，形成恶性循环。

## 四、Mitchell 的实践路径（六步）

这是他个人的"从怀疑者到受益者"历程，**对个人与小队更具操作性**。

### 第 1 步：放弃聊天机器人（Drop the Chatbot）

**主张**：立即停止用网页版聊天机器人做真正有意义的工作。

| 问题 | 说明 |
|------|------|
| 只能寄望模型"猜对" | 靠训练数据碰运气 |
| 纠错靠人反复指出 | 极其低效 |
| 棕地项目表现差 | 复制粘贴代码与输出非常痛苦 |

**结论**：要获得价值，必须用 **agent**。

**他对 agent 的最低能力定义**（很实用）：

> **① 读取文件　② 执行程序　③ 发起 HTTP 请求**

三者缺一，就不是真正的 agent。

### 第 2 步：复现自己的工作（Reproduce Your Own Work）

**方法（关键）**：**把每一份手工提交都用 agent 重做一遍**——先手动完成，再让 agent 在**看不到手动方案**的前提下产出等价结果。

> "字面意义上把活干了两遍。"

**代价**：极其痛苦、阻碍交付。**收获**：形成了真正的判断力。

他从第一性原理独立发现了三条：

1. 把会话拆成**独立、清晰、可执行的任务**，不要一个 mega-session
2. 面对模糊请求时，**把规划与执行拆成不同会话**
3. **给 agent 验证自身工作的手段**——它多半能自己修正错误、防止回归

**"负空间"洞察**（非常重要）：

> 效率提升的一部分来自**知道什么时候不该用 agent**。
> 让 agent 做它大概率会失败的事是**巨大浪费**；具备这种判断力本身就省时间。

### 第 3 步：下班前的 agent（End-of-Day Agents）

**模式**：每天固定留出**最后 30 分钟**启动 agent。

> 假设是：**"不是在我有的时间里做更多，而是在我没有的时间里做更多。"**

**三类真正有用的工作**：

| 类型 | 说明 |
|------|------|
| **深度调研** | 普查某领域的库，为每个产出多页摘要（优缺点、活跃度、口碑） |
| **并行试探模糊想法** | 多个 agent 各试一个点子，不为交付，只为第二天的"未知的未知" |
| **Issue / PR 分诊** | agent 很会用 `gh`；**明确不允许它回复**，只要报告 |

**价值**：傍晚人已疲惫、脱离心流，把这段低效精力转成第二天的**"热启动"**。

### 第 4 步：外包"灌篮"（Outsource the Slam Dunks）

**方法**：每天开工先看分诊结果，人工筛出"agent 几乎肯定能做好"的 issue，**一次只跑一个**、放后台，自己去做别的事。

**"别的事"的界定**：不是刷社交媒体，而是回到**正常的、前 AI 时代的深度思考**。

**极其重要的一条**：

> **关掉 agent 的桌面通知。**
> 上下文切换代价极高——**"何时打断 agent 是人的职责，而不是反过来。"**

### 第 5 步：工程化 Harness（Engineer the Harness）

**这是全文方法论的核心。**

**两种形式**：

| 形式 | 适用 | 做法 |
|------|------|------|
| **① 更好的隐式提示** | 简单问题（反复运行错误命令、找错 API） | 更新 `AGENTS.md` |
| **② 真正编写程序化工具** | 需要自动化 | 截图脚本、过滤测试脚本等，**通常配合一次 AGENTS.md 变更**让 agent 知道工具存在 |

**关键实例**：

> Ghostty 的 `AGENTS.md` —— **文件中每一行都源自一次 agent 的不良行为**，而该文件"几乎完全解决了全部问题"。

**背后的逻辑（两条并行）**：

> 一方面尽力**阻止 agent 再干"坏事"**；
> 另一方面尽力**让 agent 能验证自己在干"好事"**。

> 因为 **agent 在"第一次就产出正确结果"时效率最高**，而最可靠的达成方式是：**给它快速、高质量的工具，让它能自动判断自己何时错了。**

### 第 6 步：始终有一个 agent 在跑（Always Have an Agent Running）

- **自我检查**：如果当前没有 agent 在跑，就问"现在有没有什么事是 agent 能替我做的？"
- **偏好组合**：搭配**更慢、更深思的模型**，改个小东西可能要 30 分钟以上，但结果通常很好
- **并行度**：**目前只跑一个**——在"做自己享受的深度手工工作"与"看管这个有点笨却神秘高产的机器人朋友"之间取得平衡
- **现实进度**：目标仍是目标，目前约 **10–20% 的正常工作日**能做到
- **边界**：不为跑 agent 而跑 agent

## 五、两种定义的统一

| | Mitchell Hashimoto | OpenAI |
|---|---|---|
| **视角** | 个人 / 小队 | 组织 / 产品团队 |
| **路径** | **自下而上**，事故驱动 | **自上而下**，架构驱动 |
| **粒度** | 每次失误 → 一次修复 | 一套系统 → 持续演化 |
| **产出** | `AGENTS.md` + 小工具 | 分层架构 + linter + 熵管理流水线 |
| **共同内核** | **把 agent 的错误转化为永久的工程性修复** | 同左 |

> **两者的关系**：Hashimoto 定义了"单元操作"（一次修复一个错误），OpenAI 展示了"把它放大到组织规模"的样子。

## 六、效果证据

### 6.1 OpenAI 的案例数据

| 指标 | 数值 |
|------|------|
| 团队规模 | 3 人 → 7 人 |
| 周期 | 5 个月 |
| 代码量 | 约 100 万行 |
| PR 数 | 约 1500 个 |
| 人工编码 | **0 行** |
| 效率 | 约为手写代码的 **1/10 时间** |
| 起点 | **空仓库** |

> 连"管代码的代码"都是 Agent 写的：测试、CI 配置、内部工具、文档、评估框架、PR 回复、仪表盘定义。

### 6.2 更能说明问题的对照实验

**LangChain 的 Coding Agent 在 Terminal Bench 2.0 上：**

| | 分数 |
|---|---|
| 改动前 | 52.8% |
| 改动后 | **66.5%** |
| 排名 | Top 30 → **Top 5** |
| **模型** | **未更换** |

**只改了 harness**：

1. 启动时目录结构映射
2. 循环检测
3. 完成前自检清单
4. 推理强度分层（规划与验证用高推理，实现用中推理）

> **这个实验是 Harness Engineering 最强的论据**：模型不变，只改外围系统，能力跨越一个档次。

## 七、与 Prompt / Context Engineering 的关系

| 层次 | 关注 | 范围 |
|------|------|------|
| **Prompt Engineering** | 单次交互的输入质量 | 一条提示 |
| **Context Engineering** | 整个上下文窗口的组成 | 一次推理 |
| **Harness Engineering** | **环境 + 约束 + 反馈 + 生命周期** | 整个系统 |

> **Context Engineering 是 Harness 的子集，而非全部。**
> Harness 还包括：架构约束、验证闭环、熵管理、并行实例、可观测性。

```
Harness Engineering（最大）
├── Context Engineering
│     └── Prompt Engineering
├── 架构约束（linter / 分层）
├── 验证与纠正（测试 / CI / 反馈）
└── 熵管理（后台重构）
```

## 八、实施路线

### 8.1 个人（从明天就能做）

| 步 | 动作 |
|----|------|
| 1 | 建 `AGENTS.md`，**每遇一次错误就加一行** |
| 2 | 给 agent 一个能自我验证的手段（跑测试、看日志） |
| 3 | 关掉通知，改为主动间隙查看 |
| 4 | 每天下班前 30 分钟启动调研/分诊类 agent |

### 8.2 小团队（1–4 周）

| 步 | 动作 |
|----|------|
| 1 | `AGENTS.md` 控制在 **100 行内**，细节拆到 `docs/` |
| 2 | 写**结构测试**约束分层依赖 |
| 3 | lint 报错里**直接写修复方法** |
| 4 | 建立后台任务做**定期熵清理** |

### 8.3 组织（1–3 月）

| 步 | 动作 |
|----|------|
| 1 | 把 harness 做成**服务模板**（新项目默认自带） |
| 2 | 可观测性栈**按实例动态部署**，让指标可被 agent 自查 |
| 3 | 技术选型偏向"**AI 友好**"：API 稳定、训练数据足、组合性好 |
| 4 | 建立**质量评分 + 自动重构 PR** 的持续机制 |

## 九、常见误区

| 误区 | 事实 |
|------|------|
| "Harness 就是写好 system prompt" | ❌ 那只是"告知"一项，还缺约束/验证/纠正 |
| "换个更强的模型就够了" | ❌ LangChain 案例：模型不变，只改 harness，Top 30 → Top 5 |
| "AGENTS.md 越长越好" | ❌ 巨型文件会失败：挤占上下文、重点消失、迅速腐烂 |
| "先跑起来，架构以后再说" | ❌ 对 agent 恰恰相反：**没有约束，速度越快漂移越严重** |
| "技术债可以攒着一次还" | ❌ 必须像垃圾回收一样持续小额偿还 |
| "agent 出错就人工改一遍" | ❌ 那是修**这一处**；harness 是修**这一类** |
| "让 agent 自动回复 issue 更高效" | ⚠️ Hashimoto 明确**禁止**——需要人做最后判断 |
| "要一直盯着 agent" | ❌ 关掉通知，人决定何时打断，不是反过来 |

## 十、Checklist

**约束（Constrain）**
- [ ] 分层依赖方向明确且单向
- [ ] 用 linter / 结构测试**强制**执行
- [ ] lint 报错信息里含修复指引
- [ ] 约束不变量，不约束实现细节

**告知（Inform）**
- [ ] `AGENTS.md` ≤ 100 行，只做目录
- [ ] 细节拆到 `docs/` 按需加载
- [ ] 每一行规则都能追溯到一次真实失误
- [ ] 提供可观测性（日志/指标）供 agent 自查

**验证（Verify）**
- [ ] agent 能自主跑测试
- [ ] agent 能自主看日志/复现 bug
- [ ] 有"完成前自检清单"
- [ ] 规划与实现的推理强度分层

**纠正（Correct）**
- [ ] 失败有明确反馈，agent 能据此自修
- [ ] 高频错误已被工程化消除
- [ ] 有后台任务做熵清理
- [ ] 通知关闭，人主导打断时机

## 十一、总结

**Harness Engineering 完成了一个视角切换：**

| 以前 | 现在 |
|------|------|
| 模型不够强 | **系统不够稳** |
| 优化提示词 | **优化环境与反馈回路** |
| 人工检查输出 | **让 agent 自己验证** |
| 攒技术债一次还 | **持续小额偿还** |
| 人盯着 agent | **agent 跑，人给方向** |

**四条最值得记住的原则**：

1. **每次失误都要变成一次永久修复**——修"这一类"，不是"这一处"
2. **给 agent 自证清白的手段**——能自我验证的 agent 才可靠
3. **约束不变量，不约束实现**——写一次，处处生效
4. **模型是通用品，harness 才是护城河**

> 最终判断标准：**你的 agent 第一次就做对的概率，取决于你为它搭的那套系统，而不是你用的那个模型。**
