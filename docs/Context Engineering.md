# Context Engineering（上下文工程）

> **权威依据**
> ① Anthropic《Effective Context Engineering for AI Agents》，2025-09-29
> ② DAIR.AI《Context Engineering Guide》（promptingguide.ai）

## 结论

**Context Engineering 是"在 LLM 推理过程中，策划并维护最优 token 集合"的一套工程方法。** 它管的不是"一句话怎么写"，而是**模型在每一轮到底能看到什么**——系统提示、工具定义、示例、检索结果、历史消息、记忆，全部在内。

> 官方定义（Anthropic 原文）：上下文工程指**"curating and maintaining the optimal set of tokens during LLM inference"**（在 LLM 推理过程中策划与维护最优的 token 集合）。

**统一指导原则**（Anthropic 原文）：

> **找到"尽可能小的高信号 token 集合"，最大化期望结果出现的可能性。**
> （the smallest possible set of high-signal tokens that maximizes the likelihood of some desired outcome）

## 一、官方定义对照

### 1.1 Anthropic 的定义（2025-09-29）

| 项目 | 内容 |
|------|------|
| **标题** | Effective Context Engineering for AI Agents |
| **发布方** | Anthropic 工程博客 |
| **作者** | Prithvi Rajasekaran、Ethan Dixon、Carly Ryan、Jeremy Hadfield |
| **Context（上下文）** | 从 LLM 采样时所包含的 **token 集合** |
| **Context Engineering** | 在推理过程中**策划与维护**最优 token 集合的策略——不只是 prompt，还包括系统指令、工具、MCP、外部数据、消息历史 |

**核心表述**：

> 工程问题的本质是：**在 LLM 的固有限制之下，优化这些 token 的效用，从而稳定地达成期望结果。**

并强调要"**以上下文的方式思考**"（think in context）——考量模型在任一时刻可用的**整体状态**，以及该状态可能诱发的行为。

### 1.2 DAIR.AI 的定义

> **"the process of designing and optimizing instructions and relevant context for the LLMs and advanced AI models to perform their tasks effectively."**
> （设计并优化指令与相关上下文，使 LLM 及高级 AI 模型能有效完成任务的流程。）

其核心观点：

- 它是 **Prompt Engineering 的"重命名/升级"**，而非替代
- 目标：**优化填进上下文窗口的信息，同时过滤噪声**
- 本质是一个**迭代过程**，且**必须配套评测流程（eval pipeline）**

### 1.3 两者的共识

| 共识点 | 说明 |
|--------|------|
| **上下文 = 有限资源** | 不是"塞得越多越好" |
| **Prompt Engineering 是其子集** | 后者是前者的演进，不是对立 |
| **必须迭代+评测** | 没有测量就没有优化 |
| **要主动过滤噪声** | 无关信息会稀释注意力 |

## 二、与 Prompt Engineering 的关系

### 2.1 三层区分（DAIR.AI 提出）

| 层次 | 含义 | 特点 |
|------|------|------|
| **Blind Prompting（盲提示）** | 随便写一句任务描述 | 不思考上下文结构 |
| **Prompt Engineering（提示工程）** | 精心设计提示的**结构与措辞** | 考虑分隔符、示例、格式 |
| **Context Engineering（上下文工程）** | **架构完整上下文** | 提示 + 工具 + RAG + 记忆 + 状态 + 评估 |

> DAIR.AI 的说法：**"也许从一开始就该叫上下文工程"**——二者不是对立，后者是前者的**超集与下一阶段**。

### 2.2 为什么必须演进

Anthropic 的解释：

- 早期用例多是**单次分类或文本生成**，prompt 就是主要工作量
- 但当构建**多轮、长时程运行的 Agent** 时，就必须管理**整个上下文状态**
- **Agent 在循环中会不断产生新数据**，这些数据可能与下一轮推理相关，必须**循环式地精炼**

```
Prompt Engineering  → 一次性的、离散的任务
Context Engineering → 迭代的、持续策展的过程
```

### 2.3 对比表

| 维度 | Prompt Engineering | Context Engineering |
|------|-------------------|---------------------|
| **关注范围** | 单条提示的措辞 | 整个上下文窗口的组成 |
| **时间跨度** | 一次性 | 多轮循环、长时程 |
| **包含内容** | 指令、示例 | 指令 + 工具 + RAG + 记忆 + 历史 + 状态 |
| **核心动作** | 编写 | **策展（curate）** |
| **失败模式** | 说没说清楚 | 该看的没看到 / 不该看的占满 |
| **关系** | 子集 | 超集 |

## 三、为什么重要：Context Rot 与注意力预算

这是 Anthropic 文章**最扎实的理论部分**。

### 3.1 Context Rot（上下文腐化）

**"大海捞针"（needle-in-a-haystack）基准测试揭示：**

> **随着上下文窗口内 token 数量增加，模型准确召回信息的能力下降。**

**关键**：虽然有些模型退化更平缓，但**这一特性在所有模型上都存在**。

### 3.2 上下文是有限资源，边际收益递减

必须把上下文当作**有限资源**，它具有**递减的边际回报**——类比人类有限的**工作记忆**容量。

### 3.3 Attention Budget（注意力预算）

> **LLM 在解析大量上下文时会消耗一份"注意力预算"，每引入一个新 token 都会以某种程度消耗该预算。**

所以每个 token 都要"值得"。

### 3.4 架构层面的成因（为什么必然如此）

| 成因 | 解释 |
|------|------|
| **n² 的两两关系** | Transformer 每个 token 可关注所有其它 token，n 个 token 产生 **n² 组关系**；上下文变长，捕捉这些关系的能力被"摊薄" |
| **训练数据偏短** | 训练中**短序列远多于长序列**，模型对长程依赖的经验与专用参数更少 |
| **位置编码插值** | 位置编码插值（position encoding interpolation）能扩展长度，但会**降低 token 位置理解的精度** |
| **结果是梯度不是断崖** | 不是"超过长度就废"，而是**精度逐渐下降** |

> **结论**：长上下文不是免费的。**"能塞进去"不等于"能理解"。**

## 四、上下文由什么组成

### 4.1 组件清单

| 组件 | 内容 | 谁控制 |
|------|------|--------|
| **System Prompt** | 角色、规则、行为约束 | 开发者 |
| **Tools** | 工具定义（名称/描述/schema） | 开发者 |
| **Few-shot 示例** | 输入输出范例 | 开发者 |
| **用户输入** | 当前任务 | 用户 |
| **检索结果（RAG）** | 外部知识 | 系统 |
| **消息历史** | 多轮对话记录 | 系统累积 |
| **记忆 / 状态** | 外部持久化信息 | Agent 自行维护 |

### 4.2 关键认识

> **上下文中每一项都在消耗注意力预算。**
> 加一个工具定义、加一段 RAG 结果、加一条历史消息——**都会挤占模型对关键信息的注意力**。

## 五、静态组件的策略

### 5.1 System Prompt：追求"恰当高度"（Right Altitude）

**两个失败的极端**：

| 极端 | 问题 |
|------|------|
| **过度具体** | 硬编码复杂脆弱的 if-else 逻辑 → 脆弱、维护成本随时间上升 |
| **过度模糊** | 含糊的高层指导 → 缺少具体信号，或错误假设"共享上下文" |

**最佳做法**：**具体到能有效引导行为，又足够灵活，给模型以强启发式。**

**组织建议**：

```markdown
<background_information>
...
</background_information>

<instructions>
...
</instructions>

## Tool guidance
...

## Output description
...
```

> Anthropic 指出：**随着模型变强，具体格式的重要性正在下降**——*minimal ≠ short*，关键是**信息的最小集合**，而非字数最少。

**方法**：先用最强模型测试**最小 prompt**，再依据失败模式添加指令与示例。

### 5.2 Tools：最小可行工具集

工具定义是 **"Agent 与其信息/行动空间之间的契约"**。

**好工具的标准**：

| 标准 | 说明 |
|------|------|
| **自包含** | 不依赖隐藏上下文 |
| **抗错误** | 参数清晰、边界明确 |
| **用途极其清晰** | 一眼知道何时用 |
| **功能重叠最小** | 不与其它工具抢活 |

**最常见的失败模式**：

> **工具集臃肿、覆盖功能过多，导致"该用哪个工具"的决策点模糊。**

Anthropic 给出的判断标准（非常实用）：

> **如果人类工程师都无法确定某情形该用哪个工具，就不能指望 AI Agent 做得更好。**

### 5.3 Few-shot 示例：多样化 + 典型

| 反面做法 | 推荐做法 |
|----------|----------|
| 把一堆边界情况塞进 prompt，试图穷举所有规则 | 精选一组**多样、典型（canonical）** 的示例，刻画期望行为 |

> "示例对 LLM 而言是**一图胜千言**。"

### 5.4 总原则

> **对所有组件：保持"信息充分但有节制"（informative yet tight）。**

## 六、动态机制：即时检索与渐进披露

### 6.1 从"预检索"到"Just-in-time"

| 方式 | 做法 | 问题 / 优势 |
|------|------|-------------|
| **预检索（embedding 式）** | 推理前一次性检索并塞入 | 简单，但可能塞入无关内容 |
| **即时检索（just-in-time）** | 维护**轻量标识符**（文件路径、查询、链接），运行时用工具动态载入 | 更精准，但更慢 |

**Claude Code 的典型案例**：

> 对大型数据库做复杂分析时，模型**写针对性查询、存储结果、用 `head` / `tail` 等 Bash 命令分析海量数据，从不把完整数据对象载入上下文。**

**类比人类认知**：人不会背下全部资料，而是借助**文件系统、收件箱、书签**等外部索引按需取用。

### 6.2 元数据本身就是信号

引用对象的元数据能高效精炼行为：

| 信号 | 作用 |
|------|------|
| **目录层级** | `tests/test_utils.py` vs `src/core_logic/test_utils.py` 用途完全不同 |
| **命名约定** | 名字暗示用途 |
| **时间戳** | 可代理"相关性/新鲜度" |
| **文件大小** | 暗示复杂度 |

> 这些线索**同时服务于人类和 Agent**。

### 6.3 渐进披露（Progressive Disclosure）

> 让 Agent 自主导航与检索，可**逐层组装理解**——工作记忆中只保留必要内容。

**机制**：

```
文件大小 → 暗示复杂度
命名     → 暗示用途
时间戳   → 代理相关性
      ↓
Agent 决定要不要深入看
      ↓
只把必要的读进上下文
```

**效果**：**"自管理的上下文窗口"**——聚焦相关子集，而非淹没在详尽却可能无关的信息中。

### 6.4 权衡与混合策略

| 代价 | 说明 |
|------|------|
| **更慢** | 运行时探索比预计算检索慢 |
| **需要好的工具与启发式** | 否则 Agent 会滥用工具、钻牛角尖（chasing dead-ends）、漏掉关键信息 |

**混合策略（推荐）**：

| 部分 | 方式 |
|------|------|
| 稳定内容 | **预置**进上下文（如 `CLAUDE.md`） |
| 动态内容 | 用 `glob`、`grep` 等原语**按需导航** |

> 这能绕开"**陈旧索引**"与"**复杂语法树**"的问题。
> 适合**内容动态性较低**的领域（如法律、金融）。

### 6.5 趋势判断

> **"做能起作用的最简单的事"（do the simplest thing that works）。**
> 随模型能力提升，Agentic 设计将倾向"让聪明的模型智能行事"，人工策展逐步减少。

## 七、长时程任务的三大技术

**长时程任务的定义**：需要 Agent 在动作序列中保持连贯性，且 token 数**超出上下文窗口**（如大型代码库迁移、综合研究，跨度数十分钟到数小时）。

> **关键判断**：**等待更大的上下文窗口并非显然的解法**——在可预见的未来，任何规模的窗口仍会受 **context pollution（上下文污染）** 困扰。

### 7.1 Compaction（压缩）

**做法**：当对话接近上下文上限时，对其**总结**，用摘要**重新开启新窗口**。

**Claude Code 的实现细节**：

| 保留 | 丢弃 |
|------|------|
| 架构决策 | 冗余的工具输出 |
| 未解决的 bug | 重复消息 |
| 实现细节 | — |

压缩后：**"压缩摘要 + 最近访问的 5 个文件"** 继续工作。

**风险**：过度激进的压缩会丢失"重要性稍后才显现"的微妙上下文。

**调优顺序**：

```
先最大化 recall（确保捕获每条相关信息）
        ↓
再提升 precision（剔除多余内容）
```

**最低垂的果实 —— Tool Result Clearing（工具结果清理）**：

> **历史上早已调用过的工具，Agent 何必再看原始结果？**
> 这是**最安全、最轻量**的压缩形式。

### 7.2 Structured Note-taking（结构化笔记）

**做法**：Agent 定期把笔记写到上下文窗口**之外**的持久化记忆，之后再拉回。

**典型形态**：

- Claude Code 的 **to-do list**
- 自定义 Agent 维护的 **`NOTES.md`**

**Claude 玩 Pokémon 的著名案例**：

> Agent 在数千游戏步中维持精确统计——"过去 1,234 步我在 1 号道路训练，皮卡丘已升 8 级，目标 10 级"。
> **在没有任何记忆结构提示的情况下**，它自行绘制已探索区域地图、记住已解锁成就、维护战斗策略笔记。
> **上下文重置后**，Agent 读取自己的笔记继续数小时计的探索——这种连贯性，单靠把所有信息留在窗口内**不可能实现**。

**产品化**：Sonnet 4.5 发布时，Claude Developer Platform 公测了 **memory tool**（基于文件系统），支持跨会话维持项目状态。

### 7.3 Sub-agent Architectures（子代理架构）

**做法**：让**专用子代理**在**干净的上下文窗口**中处理聚焦任务，主 Agent 以高层计划协调。

**关键数字**：

> 每个子代理可能探索**数万 token**，但**只返回 1,000–2,000 token 的蒸馏摘要**。

**收益**：清晰的关注点分离——详细检索上下文隔离在子代理内部，主 Agent 专注综合与分析。

> 该模式在复杂研究任务上**显著优于单 Agent 系统**。

### 7.4 三种技术怎么选

| 技术 | 适用场景 |
|------|----------|
| **Compaction** | 需要大量**来回往复（back-and-forth）** 的任务，保持对话流 |
| **Structured Note-taking** | 有**清晰里程碑**的迭代式开发 |
| **Sub-agent 架构** | **并行探索**能带来收益的复杂研究与分析 |

## 八、工程落地：七层上下文架构（DAIR.AI）

以"多智能体 deep research 应用"为例，逐层拆解：

| 层 | 组件 | 关键做法 |
|----|------|----------|
| **1** | **System Prompt / Instructions** | 高层任务说明 + 范围界定。**多数人止步于此，但远不够** |
| **2** | **User Input** | 用**分隔符**包裹，如 `<user_query>...</user_query>` |
| **3** | **Structured I/O** | 显式列出每个字段的类型、**取值范围**、示例 |
| **4** | **Tools** | 动态信息（时间等）**按需调用**，不无条件注入 |
| **5** | **RAG & Memory** | 缓存可复用结果（如子查询向量库）降低延迟成本 |
| **6** | **States & History** | 保留修订记录、各代理结果，支持多轮自我纠正 |
| **7** | **Advanced** | 压缩、上下文管理、安全、评估（持续演进） |

### 8.1 最容易被忽视的第 3 层：结构化输出

**DAIR.AI 给出的经典反例**：

> 若不说清 `priority` 是 **1–5 分制**，模型可能**自行采用 1–10 分制**。

**正确做法**：

```
id: str
query: str
source_type: str
time_period: Optional[str] = None
domain_focus: str
priority: int   # 1 (highest) to 5 (lowest)   ← 必须写清量纲
```

> 并用 **JSON 示例**驱动 output parser 自动生成 schema。
> 作者称这是"**被很多 AI 开发者忽视的低估环节**"，对**多组件工作流的一致性**尤其关键。

### 8.2 第 4 层的洞察：动态信息应做成工具

**为什么注入当前时间？**

> 否则模型会**猜测日期**，导致时间范围（`start_date` / `end_date`）推断错误，搜索结果质量下降。

但**不应该无条件注入**——只在查询涉及时效时才取。

> 这迫使构建者对"**传什么上下文、何时传**"做明确决策，从而**消除假设与不准确**。

### 8.3 一句值得记住的话

> **"Creative and novel context engineering is the moat!"**
> （创造性的上下文工程才是护城河）

## 九、评估：没有测量就没有优化

两份来源都强调这一点。

| 来源 | 表述 |
|------|------|
| **DAIR.AI** | "如果你不测量，怎么知道上下文工程是否奏效？" → **必须建 eval pipeline** |
| **Anthropic** | 压缩策略要在**复杂 Agent trace 上仔细调 prompt**，先 recall 后 precision |

### 评估要点

| 评估什么 | 怎么评估 |
|----------|----------|
| **上下文是否被稀释** | 检查是否有过期、无关信息堆积 |
| **检索是否有效** | Recall@k、命中率 |
| **压缩是否失真** | 压缩后性能下降幅度 |
| **端到端是否变好** | 真实任务成功率 |

## 十、常见反模式

| 反模式 | 问题 | 改进 |
|--------|------|------|
| **能塞就塞** | 触发 Context Rot，注意力被摊薄 | 只放高信号 token |
| **工具越多越好** | 决策点模糊，选错工具 | 最小可行工具集 |
| **system prompt 写成 if-else** | 脆弱、难维护 | 保持"恰当高度" |
| **示例堆边界情况** | 试图穷举规则 | 用多样化典型示例 |
| **无条件注入动态信息** | 浪费 token、造成混淆 | 做成工具按需调用 |
| **不说清量纲/范围** | 模型自创 1–10 分制 | 显式写明范围 |
| **无限累积历史** | 窗口必然爆 | 压缩 / 笔记 / 子代理 |
| **只靠更大窗口解决** | 污染问题不会消失 | 用工程手段管理 |
| **不做评测** | 改了不知道好坏 | 建 eval pipeline |

## 十一、Checklist

**静态组件**
- [ ] System Prompt 处于"恰当高度"（不过细、不过糊）
- [ ] 用分区标签组织（`<instructions>`、`## Tool guidance` 等）
- [ ] 工具集精简，无功能重叠
- [ ] 示例多样化且典型

**动态机制**
- [ ] 稳定内容预置，动态内容即时取
- [ ] 利用元数据（路径/命名/时间戳）传递信号
- [ ] 实现渐进披露，避免一次性全载

**长时程**
- [ ] 有压缩策略（先 recall 后 precision）
- [ ] 清理历史工具结果
- [ ] 有外部笔记/记忆机制
- [ ] 复杂任务考虑子代理

**工程**
- [ ] 有 eval pipeline
- [ ] 监控上下文是否被稀释
- [ ] 定期清理过期信息

## 十二、总结

**Context Engineering 把"上下文"从"提示词的容器"重新定义为"稀缺的注意力预算"。**

它的完整方法论可以概括为一条主线：

```
静态组件（system prompt / tools / examples）
        ↓ 保持"信息充分但有节制"
动态机制（just-in-time 检索 / 渐进披露）
        ↓ 用到才取
长时程技术（压缩 / 笔记 / 子代理）
        ↓ 突破窗口限制
统一目标：最小的、高信号的 token 集合
```

**四条最值得记住的原则**：

1. **上下文是有限资源**，边际收益递减，不是越多越好
2. **做能起作用的最简单的事**——不要为了"更先进"而过度设计
3. **最小 ≠ 最短**——关键是高信号，不是字数少
4. **不测量就等于没优化**——必须有 eval pipeline

> 最终判断标准只有一句：**在每一轮推理中，究竟应该让模型看到哪些 token。**
