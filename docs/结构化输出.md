# 结构化输出（Structured Outputs）

> **权威依据**
> ① **Anthropic**《Structured outputs》官方文档（公开 Beta）
> ② **OpenAI** Structured Outputs（`json_schema` + `strict`）
> ③ 本知识库：`Function Calling.md`、`Function Calling VS Tool Calling.md`、`Context Engineering.md`

## 结论

**结构化输出不是"让模型输出 JSON"，而是"在解码阶段禁止它输出不符合 Schema 的内容"。**

| | 提示词法 | **结构化输出** |
|---|---|---|
| 机制 | **概率性引导**（soft） | **约束解码 / 编译语法**（hard） |
| 失败模式 | 非法 JSON、缺字段、`"2"` vs `2` | 正常路径下**结构保证** |
| 需要重试吗 | 需要（解析失败就重试） | **不需要**（因 schema 违规） |

> **一句话**：**提示词法在"求"模型，结构化输出在"限"模型。**

**但有一条最重要、也最容易忽略的提醒**：

> **发给模型的是 Schema 的"简化版"**——不支持的关键字会被 SDK **删掉并改写成 description**。
> **所以你必须在客户端用完整 Schema 再校验一次。**

## 一、为什么需要：提示词法的三种失败

```python
# 你在 prompt 里写："请严格输出 JSON，字段 name 和 age"
```

| 失败 | 表现 |
|------|------|
| **语法错** | `{"name": "张三", "age": 30,}` 尾逗号 / 缺引号 / 前缀废话 |
| **结构错** | 缺 `age`、多出 `email`、`age` 变成 `"30"` |
| **枚举错** | 要 `high/medium/low`，它给了 `very high` |

**为什么"更强的模型"解决不了**：

> 模型是**逐 token 采样**的。在它写 `{"age": "` 的那一刻，**它并不知道后面要写数字还是字符串**——因为没有机制约束它。
>
> **结构化输出就是在采样层把非法分支屏蔽掉。**

## 二、核心机制：约束解码

```
普通生成：  概率分布 → 采样任意 token → 可能非法
约束解码：  概率分布 → 按语法状态屏蔽非法 token → 只有合法 token 可选
```

**关键含义**：

| 特性 | 说明 |
|------|------|
| **不是提示词** | Schema 通过 **API 参数**传入，不靠 prompt 描述 |
| **不是后处理** | 不是"生成完再修 JSON"，是**生成时就合法** |
| **不需要 "只输出 JSON" 这类指令** | 指令是多余的 |
| **代价是表达力** | 很多 JSON Schema 关键字**做不到**（见第六、七章） |

## 三、OpenAI：`json_schema` + `strict`

### 3.1 两种使用形态

```json
// A. 约束响应格式
"response_format": {
  "type": "json_schema",
  "json_schema": {
    "name": "contact_info",
    "strict": true,
    "schema": { ... }
  }
}

// B. 约束工具参数
"tools": [{
  "type": "function",
  "function": {
    "name": "get_weather",
    "strict": true,
    "parameters": { ... }
  }
}]
```

### 3.2 `strict: true` 的两条硬约束（最容易报错）

**每个 object 必须同时满足**：

| 约束 | 说明 |
|------|------|
| **① `additionalProperties: false`** | 必须**显式声明**，缺失直接 `invalid_schema` |
| **② 所有属性都必须出现在 `required` 里** | **不存在"可选字段"** |

**要表达"可选"，用 `null` 联合类型**：

```json
{
  "type": "object",
  "properties": {
    "name":  { "type": "string" },
    "email": { "type": ["string", "null"] }
  },
  "required": ["name", "email"],
  "additionalProperties": false
}
```

> **嵌套对象、数组内对象、`$defs` 里的对象同样适用。**

### 3.3 支持 / 不支持的关键字（**这是最大的坑**）

| 类别 | 状态 |
|------|------|
| `type` / `properties` / `required` / `items` / `enum` / `anyOf` / `$defs` / `$ref`（递归） | ✅ 支持 |
| 字符串 `format`（`date-time`、`email`、`uuid`、`ipv4` 等） | ✅ 支持 |
| **`minLength` / `maxLength`** | ❌ **不支持** |
| **`minItems` / `maxItems` / `uniqueItems`** | ❌ **不支持** |
| **`minimum` / `maximum` / `multipleOf`** | ⚠️ 部分支持（**依版本变化，需核对**） |
| `allOf` / `not` / `if-then-else` | ❌ 不支持 |
| `patternProperties` / `propertyNames` | ❌ 不支持 |

> ⚠️ **这些不支持的约束会被静默忽略**——你不校验，就没有任何东西在保护你。

### 3.4 JSON mode vs Structured Outputs

| | JSON mode（`json_object`） | **Structured Outputs** |
|---|---|---|
| 保证 | 只是"语法合法 JSON" | **语法 + 完全符合 Schema** |
| 传 Schema | ❌ 要写在 prompt 里 | ✅ API 参数 |
| 提示词要求 | 必须出现 "JSON" 字样 | 无 |
| 幻觉字段 | 会有 | 不会 |
| 拒绝处理 | 无专门字段 | 有 `refusal` |

> **一句话**：**JSON mode 是"格式像 JSON"，Structured Outputs 是"结构被约束"。**

## 四、Anthropic：两条独立路径

### 4.1 路径一：JSON 输出（`output_format`）

```python
response = client.beta.messages.create(
    model="claude-sonnet-4-5",
    max_tokens=1024,
    betas=["structured-outputs-2025-11-13"],
    messages=[{"role": "user", "content": "提取这份名片的信息"}],
    output_format={
        "type": "json_schema",
        "schema": transform_schema(ContactInfo),   # 原始 dict 或 Pydantic 类
    },
)

import json
data = json.loads(response.content[0].text)     # 保证不失败
```

**三个要点**：

| 要点 | 说明 |
|------|------|
| **是普通文本块** | 不是 `tool_use` 块，仍在 `content[0].text` |
| **仍需 `json.loads`** | 但**保证不失败** |
| **可传 Pydantic / Zod** | SDK 负责转换成 JSON Schema |

> ⚠️ **参数名已迁移**：较早文档为顶层 **`output_format`**，较新版本**已移到 `output_config.format`**。
> **接入前必须核对当前版本**——这是最容易写错的一处。

### 4.2 路径二：严格工具（`strict: true`）

```json
{
  "name": "get_weather",
  "description": "...",
  "input_schema": { ... },
  "strict": true
}
```

**语义保证**：

- `tool_use.input` **严格遵循** `input_schema`
- `tool_use.name` **必定合法**
- 消除 `"2"` vs `2` 类型错配与缺字段
- **无需重试校验**

### 4.3 两条路径的区别（"校验输入还是输出"）

| | JSON 输出（`output_format`） | 严格工具（`strict: true`） |
|---|---|---|
| **约束对象** | Claude 的**响应内容** | 生成的**工具名与参数** |
| **校验位置** | 输出侧 | **输入侧（你的函数入参）** |
| **结果位置** | `content[0].text` | `content[x].input` |
| **典型场景** | 数据抽取、报告、API 响应 | **Agent 工作流、类型安全函数调用** |

> **实务建议**：**Agent 场景优先用"严格工具"**——因为工具参数错了会直接导致错误动作，后果比"格式难看"严重得多。

## 五、三方对照

| | **OpenAI** | **Anthropic** | **Gemini** |
|---|---|---|---|
| **响应约束** | `response_format.json_schema` | `output_format` / `output_config.format` | `responseSchema` |
| **工具严格模式** | `function.strict: true` | `strict: true` | `functionDeclarations` + schema |
| **后端模型** | 支持 Pydantic/Zod 转换（SDK） | ✅ | ✅ |
| **拒绝字段** | `refusal` | `stop_reason: "refusal"` | — |
| **成熟度** | GA | **公开 Beta（需 beta header）** | 依模型 |

> **通用结论**：**三家都能做，但参数名、Beta 头、Schema 子集全都不同。**
> 所以**一定要在自建抽象层后面**，别把某家的参数名写进业务代码。

## 六、最大的坑：发出去的是"简化版 Schema"

> **Anthropic 官方 SDK 的自动降级策略**（这条最关键）：

| 步骤 | 动作 |
|------|------|
| 1 | **剔除不支持的约束** |
| 2 | **把约束改写成 `description`**（如 "Must be at least 100"） |
| 3 | 所有 object **自动补 `additionalProperties: false`** |
| 4 | 过滤 `format` 白名单 |
| 5 | **建议你在客户端用原始 Schema 做最终校验** |

**含义**：

```
你写的 Schema（含 minimum: 100）
        ↓ SDK 转换
发给模型的 Schema（minimum 被删，写进 description）
        ↓ 模型生成
"age": 5        ← 模型端没有被约束！
        ↓ 你的客户端
❌ 校验失败（如果你做了校验）
```

> **这是一个"看起来安全其实不安全"的陷阱。**
> **Schema 保证的是"结构"，不是"业务规则"。**

### 6.1 正确做法

| 层 | 负责 |
|----|------|
| **Schema（发给模型）** | 类型、必填、枚举、结构 |
| **客户端校验** | **数值范围、长度、业务规则、跨字段依赖** |

```python
from pydantic import BaseModel, Field, ValidationError

class Person(BaseModel):
    name: str
    age: int = Field(ge=0, le=150)   # ← 这个约束模型端看不到

raw = json.loads(response.content[0].text)
try:
    person = Person.model_validate(raw)      # ← 真正的守门人
except ValidationError as e:
    # 让模型重试，并把错误信息回灌
    fix = llm_fix(raw, e.errors())
```

## 七、两种"HTTP 200 但其实坏了"的情况

> **必须单独分支处理，不能默认 `content` 一定存在且完整。**

| 情况 | 判断条件 | 表现 |
|------|----------|------|
| **① 安全拒答** | OpenAI: `message.refusal` 非空<br>Anthropic: `stop_reason: "refusal"` | **Schema 保证失效**，输出可能不合规，**token 照常计费** |
| **② 被截断** | `finish_reason` / `stop_reason == "max_tokens"` | **JSON 不完整**，解析必失败 |

### 7.1 标准处理模板

```python
msg = resp.choices[0].message
finish = resp.choices[0].finish_reason

# ① 先看拒绝
if getattr(msg, "refusal", None):
    handle_refusal(msg.refusal)

# ② 再看截断
elif finish == "length":
    handle_truncation()        # 提高 max_tokens 重试，不要盲目重试

# ③ 才敢解析
else:
    data = json.loads(msg.content)
    validated = MySchema.model_validate(data)   # 客户端再校验一次
```

> **Anthropic 侧同理**：检查 `stop_reason` 是否为 `"refusal"` 或 `"max_tokens"`。

### 7.2 为什么拒答会绕过 Schema

> **安全拒答的优先级高于 Schema 保证。**
> 模型不会为了满足格式而硬凑一个它认为不该给的内容。

## 八、性能与成本

### 8.1 Schema 编译延迟（Anthropic 官方）

| 特性 | 说明 |
|------|------|
| **首次使用** | 有**额外延迟**（服务端编译语法） |
| **缓存时长** | **24 小时**（自最后一次使用起） |
| **缓存失效条件** | ① Schema 结构变化　② **请求中的工具集合变化**　③ （名/description 变化**不**失效） |

> **推论**：**高频变更 Schema、或动态增删工具，会持续吃编译开销。**
> 所以 **Schema 要稳定**，工具集也**不要每次请求都变**。

### 8.2 Token 开销

| 开销 | 说明 |
|------|------|
| **Schema 本身** | 会注入 system prompt，**额外消耗输入 token** |
| **改 Schema 会打断 prompt cache** | Anthropic：修改 `output_format` **使该会话的 prompt cache 失效** |

> **这是一个隐藏的冲突**：结构化输出和 prompt caching 会互相打架。
> **对策**：把 Schema 定义**放在稳定前缀的最后**，别在中间插变量。

### 8.3 为什么"改了没用"

| 症状 | 原因 |
|------|------|
| 首次调用变慢 | Schema 编译（正常） |
| 改了 Schema 后突然变贵 | **prompt cache 被冲掉** |
| 加了很多工具后变慢 | 工具集合变化 → **Schema 缓存失效** |

## 九、Schema 设计原则

### 9.1 五条硬建议

| # | 原则 | 理由 |
|---|------|------|
| **1** | **用 `enum` 代替自由文本** | 最划算的约束：分类、状态、优先级 |
| **2** | **扁平优先，减少嵌套** | 嵌套越深越容易触发 "too complex" |
| **3** | **用 `["string","null"]` 表达可选** | strict 模式下没有"可选字段" |
| **4** | **`description` 写清单位与格式** | 因为**降级后的约束只能靠 description 传达** |
| **5** | **不在 Schema 里表达业务规则** | 模型端看不到，必须客户端校验 |

### 9.2 `description` 的正确写法（最容易被敷衍的地方）

```json
// ❌ 敷衍
"priority": { "type": "integer", "description": "优先级" }

// ✅ 有效
"priority": {
  "type": "integer",
  "description": "优先级，1-5 的整数，1 最高，5 最低。必须是整数，不要用 1-10 分制。"
}
```

> **Context Engineering 里提过的一个真实坑**：不说清是 1–5 分制，模型就可能**自行采用 1–10 分制**。
> 结构化输出保证它**是整数**，但**保证不了范围**。

### 9.3 扁平 vs 嵌套

```json
// ❌ 嵌套过深（易触发复杂度上限）
{ "result": { "data": { "items": [{ "meta": { "tags": [...] } }] } } }

// ✅ 扁平（一层数组 + 简单对象）
{ "items": [{ "id": "...", "title": "...", "tags": ["a","b"] }] }
```

## 十、Pydantic / Zod 工作流（推荐）

### 10.1 Python + Pydantic

```python
from pydantic import BaseModel, Field
from typing import Literal


class RiskItem(BaseModel):
    clause: str = Field(description="合同原文条款")
    level: Literal["high", "medium", "low"] = Field(description="风险等级")
    reason: str = Field(description="判定理由，不超过 50 字")


class RiskReport(BaseModel):
    contract_name: str
    risks: list[RiskItem]
    overall: Literal["approve", "review", "reject"]


# OpenAI
resp = client.chat.completions.create(
    model="...",
    messages=[...],
    response_format={
        "type": "json_schema",
        "json_schema": {
            "name": "risk_report",
            "strict": True,
            "schema": RiskReport.model_json_schema(),   # ← 自动转换
        },
    },
)

report = RiskReport.model_validate_json(resp.choices[0].message.content)
```

> **好处**：**Schema 定义与校验用同一份代码**，不会两边漂移。

### 10.2 TypeScript + Zod

```typescript
import { z } from "zod";

const RiskItem = z.object({
  clause: z.string().describe("合同原文条款"),
  level: z.enum(["high", "medium", "low"]).describe("风险等级"),
  reason: z.string().describe("判定理由，不超过 50 字"),
});

const RiskReport = z.object({
  contractName: z.string(),
  risks: z.array(RiskItem),
  overall: z.enum(["approve", "review", "reject"]),
});
```

## 十一、在 Agent 中的三种用法

### 11.1 用法一：工具参数（最重要）

```
"strict": true  →  工具参数 100% 合法  →  不用 try/except 兜底
```

> **Agent 场景里这是收益最大的一处**：工具参数错了会**直接导致错误动作**，比"输出格式难看"严重得多。

### 11.2 用法二：最终输出

```
用户："把这份合同的风险整理成表"
→ 强制输出符合 RiskReport Schema 的 JSON
→ 前端直接渲染表格，不需要二次解析
```

### 11.3 用法三：用"强制调用工具"做结构化输出（跨厂商通用技巧）

> **对于没有原生结构化输出的模型，这是最稳的做法。**

```json
{
  "tools": [{
    "name": "submit_result",
    "description": "提交最终结果。必须调用此工具，不要用文字回答。",
    "input_schema": { ...你的 Schema... }
  }],
  "tool_choice": { "type": "tool", "name": "submit_result" }
}
```

**原理**：**工具参数本来就是结构化的**，强制调用 = 强制结构化输出。

| 优点 | 缺点 |
|------|------|
| 跨厂商通用 | 多一次工具调用语义 |
| 可配合严格模式 | 部分模型不支持强制 `tool_choice` |

### 11.4 用法四：中间结果结构化（Plan 场景）

> `Agent规划与任务分解.md` 里的计划列表，本质也是结构化输出：

```python
class PlanStep(BaseModel):
    id: int
    task: str
    depends_on: list[int]
    acceptance: str    # 验收标准——没有这个字段的计划是废的


class Plan(BaseModel):
    steps: list[PlanStep]
```

**收益**：计划**可校验**（依赖是否成环、步数是否超限）、可并行、可恢复。

## 十二、什么时候不用结构化输出

| 场景 | 原因 |
|------|------|
| **自由文本创作** | 文章、邮件、文案——结构限制反而有害 |
| **需要引用（Citations）** | Anthropic：与 JSON 输出**同开会 400** |
| **需要 Message Prefilling** | Anthropic：与 JSON 输出**不兼容** |
| **需要极简响应** | Schema 会注入 system prompt 增加 token |
| **Schema 极其复杂** | 会触发 "Schema is too complex" |

## 十三、常见坑

| # | 坑 | 后果 | 解药 |
|---|----|------|------|
| **1** | **以为 `minimum` 生效了** | 模型给出越界值 | **客户端用完整 Schema 校验** |
| **2** | **没处理 `refusal`** | 拿到 `null` 内容崩掉 | 先判拒绝再解析 |
| **3** | **没处理 `max_tokens` 截断** | JSON 不完整解析失败 | 检查 `finish_reason` |
| **4** | **以为"可选字段"能省** | `strict` 下必须全填 | 用 `["type","null"]` |
| **5** | **忘了 `additionalProperties: false`** | 手写 Schema 直接 400 | SDK 会自动补，手写要注意 |
| **6** | **频繁改 Schema** | 每次重新编译，延迟 + 成本 | Schema 要稳定 |
| **7** | **动态增删工具** | Schema 缓存失效 | 工具集保持稳定 |
| **8** | **参数名按旧文档写** | Anthropic `output_format` → `output_config.format` 已迁移 | 核对当前版本文档 |
| **9** | **用 Schema 表达跨字段规则** | 模型端做不到 | 客户端校验 |
| **10** | **以为结构对 = 内容对** | 枚举值选错、理由编造 | **结构保证不等于语义正确** |
| **11** | **Schema 嵌套太深** | "too complex" 400 | 扁平化 |
| **12** | **只用 JSON mode** | 幻觉字段、缺字段 | 用真正的 `json_schema` |

## 十四、Checklist

**设计 Schema**
- [ ] 用 `enum` 约束所有分类/状态字段
- [ ] 所有可选字段用 `["T","null"]`
- [ ] 每个 object 都有 `additionalProperties: false`
- [ ] `description` 写清**单位、范围、格式**
- [ ] 嵌套不超过 3 层
- [ ] **没有**用 Schema 表达业务规则

**接入**
- [ ] 用 Pydantic / Zod **单一来源**定义 Schema
- [ ] 核对当前版本的参数名（`output_format` vs `output_config.format`）
- [ ] 需要 beta header 的已带上
- [ ] 工具参数开了 `strict: true`
- [ ] Schema 尽量**稳定**，避免频繁变更

**运行时**
- [ ] 先判 **refusal**
- [ ] 再判 **max_tokens / length**
- [ ] 然后才 `json.loads`
- [ ] **客户端用完整 Schema 再校验**
- [ ] 校验失败有**回灌重试**（把错误信息给模型）
- [ ] 有重试上限

**观测**
- [ ] 统计 schema 违规率（**正常应为 0**，非 0 说明走了降级路径）
- [ ] 统计 refusal 率
- [ ] 统计截断率
- [ ] 关注首次调用延迟与缓存失效

## 十五、总结

**三句话：**

| 层 | 保证什么 |
|----|----------|
| **提示词法** | 什么都不保证 |
| **JSON mode** | 保证**是合法 JSON** |
| **Structured Outputs** | 保证**符合 Schema 的结构** |
| **客户端校验** | 保证**符合业务规则** |

**五条最值得记住的原则**：

1. **结构化输出保证结构，不保证内容** —— 枚举值仍可能选错
2. **发出去的是简化版 Schema** —— 客户端必须用完整版再校验
3. **两种"200 但坏了"** —— `refusal` 与 `max_tokens`，必须单独分支
4. **Schema 要稳定** —— 频繁变更会被编译延迟和缓存失效惩罚
5. **Agent 场景优先约束工具参数** —— 参数错的后果比格式错严重得多

> **最后一句话**：
> **结构化输出把"祈祷模型听话"变成了"引擎强制它听话"——但它只强制了形状，没强制内容。**
> 真正的守门人，永远是你在客户端写的那行 `validate()`。
