# 前端转 Agent 应用开发 · 学习与实战计划

> **适用对象**：有前端经验（TypeScript / Vue3）、**Agent 零基础**、目标是在简历上有一个能讲的 Agent 项目
> **技术栈**：Python FastAPI（后端） + TypeScript Vue3（前端）
> **本机环境**：Python **3.12.8**、Node **22.22.0**（已就绪）
> **教材**：本仓库 `docs/` 下 **44 篇**文档（已按阶段映射好，不用另找资料）
> **生成日期**：2026-11-07

## 结论：这套计划怎么设计的

**只做一个项目，让它从"能聊天"长到"能上线"。**

```
S0 地基 ──→ S1 直连 ──→ S2 Agent ──→ S3 RAG ──→ S4 记忆
                                                    │
                S9 简历项目 ←── S8 部署 ←── S7 评测 ←── S5 前端
                                     │
                                   S6 结构化
```

每个阶段产出的**都是同一个项目的零件**，不是 9 个独立 demo。

> **这是关键决策**：
> 做 9 个 demo 的人，简历上写不出任何一条；
> 做 1 个项目长 9 轮的人，简历上能写 9 条，因为**每个零件都是真的在跑**。

## 三个阶段目标（别再往后想）

| 里程碑 | 时间 | 达到什么 | 能做什么 |
|--------|------|----------|----------|
| **M1 · 能跑通** | 第 1–3 周 | Python + FastAPI + LLM 直连 | 做一个流式对话页面（前后端都是自己写的） |
| **M2 · 是 Agent** | 第 4–8 周 | 工具调用 + RAG + 记忆 | Agent 会自己调工具查资料，不再是纯聊天 |
| **M3 · 能上简历** | 第 9–17 周 | 评测 + 安全 + 部署 | **有线上地址、有数据、有架构图的项目** |

## 怎么用这份计划

### 1. 每个阶段开始前：先读知识库对应文档

`docs/` 里那 44 篇是**答案**，这份计划是**题目顺序**。
**不要先读书再动手**——先看阶段任务，卡住了再去查对应文档。

> 理由：Agent 开发的坑，**读书时看不出来，写代码时全冒出来**。

### 2. 每个阶段必须产出可运行的东西

**验收标准不通过，不进下一阶段。** 每个阶段都写了验收标准，那不是建议，是门槛。

### 3. 保留"失败记录"

每个阶段建一个 `notes.md`，记三件事：

```markdown
## S2 失败记录
- 现象：工具报错后模型不重试，直接放弃
- 原因：错误信息我没放进 observation，模型以为成功了
- 修复：把 exception 序列化成 "ERROR: ..." 塞回 messages
- 一句话教训：**错误也必须是一条消息**
```

> **这东西在面试时比代码更值钱**——能讲清踩坑的人，比能背 API 的人可信得多。

## 三个不要（新手最容易犯）

| 不要 | 为什么 |
|------|--------|
| **不要一上来就用 Agent 框架** | 你调不动你不理解的东西。S2 必须手写循环，之后爱用什么用什么 |
| **不要追求"效果完美"** | S3 的 RAG 目标是"能测出 80% 召回"，不是"比 ChatGPT 好" |
| **不要跳过 S7 评测** | 没有评测的项目，面试官问一句"你怎么知道它好用"就穿帮了 |

## 最后一句

**前端转 Agent，你最大的优势不是算法，是"能把 Agent 做成产品"。**

市面上会调 API 的人很多，能把它做成**用户愿意用、你也讲得清**的人很少。你的 Vue3 能力、你对交互的理解、你对"加载态/错误态/空态"的直觉——这些在 Agent 产品里比 Prompt 技巧更稀缺。

**别去补短板（数学、训练），把长板（产品化 + 全栈）打到最长。**
