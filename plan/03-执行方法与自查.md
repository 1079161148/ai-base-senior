# 执行方法与自查

> 这份文件解决一个问题：**"我知道该学什么，但我坚持不下来/不知道有没有学会"。**

## 一、每周固定节奏

| 时间 | 做什么 | 时长 |
|------|--------|------|
| **周一** | 读本阶段任务清单，拆成 3–5 个小任务，写进 todo | 20 min |
| **周二–周五** | 每天推进 1 个小任务（**宁可小，必须完成**） | 2 h/天 |
| **周六** | 整块攻坚（做最难的那个任务）+ 写 `notes.md` | 4 h |
| **周日** | 跑验收清单，**不过就补，不往后走** | 2 h |

> **关键**：**每天必须有一个"能做出来"的成果**，哪怕只是"接口返回对了"。
> 连续三天没有任何产出，就是在滑坡。

## 二、卡住时的三级求助

> **别一卡住就问 AI。这会让你失去"自己定位问题"的能力——而这是工程师最核心的能力。**

### 第 1 级：自己查（15 分钟）

| 动作 | 目的 |
|------|------|
| **读完整报错**（从第一行到最后一行） | 80% 的答案在报错里 |
| 打印中间变量 | 确认你的假设 |
| 看官方文档对应章节 | 别搜博客先搜官方 |
| 查 `docs/` 对应文档 | 你的知识库就是为这个准备的 |

### 第 2 级：缩小范围（15 分钟）

```python
# 不要问"为什么不行"，要问"到底哪一步不行"
print("1. 拿到输入了吗", user_input)
print("2. 模型返回什么", resp)
print("3. 工具被调用了吗", [c.name for c in resp.tool_calls])
print("4. 工具返回什么", result)
print("5. 消息栈现在长什么样", messages)
```

> **能定位到"哪一行"，问题就已经解决一半了。**

### 第 3 级：问 AI / 问人

提问必须包含：

```
1. 我想做什么
2. 我写了什么（贴最小可复现代码）
3. 报错是什么（贴完整栈）
4. 我已经试过什么，排除了什么
5. 我怀疑是什么原因
```

> **没有第 4、5 条的提问，得到的答案通常没用**——因为对方不知道你已经排除了什么。

## 三、阶段结束自查清单

每个阶段结束时，逐项打勾。**不允许"差不多"。**

```markdown
## S2 结束自查
- [ ] 验收标准全部通过（对照 01 文件）
- [ ] notes.md 里至少 3 条踩坑记录
- [ ] 代码能跑起来（不是"理论上能跑"）
- [ ] 能不看代码讲清这一阶段的核心机制
- [ ] 能回答"如果这一步失败会怎样"
- [ ] 已提交 git，commit 历史清晰
```

### 判断"能讲清"的标准

**不看代码，用 60 秒讲给一个不懂的人听，他能复述出大意。**

自测问题举例：

| 阶段 | 自测问题 |
|------|----------|
| S0 | `async def` 里调同步函数会怎样？为什么？ |
| S1 | 前端点"停止"后，后端怎么知道要停？ |
| S2 | 为什么 assistant 消息必须放进 messages？不放会怎样？ |
| S3 | 为什么纯向量检索查不到错误码？ |
| S4 | 上下文超了，你先砍哪部分？为什么？ |
| S5 | 为什么打字机效果不能用每字符 setState？ |
| S6 | 计划为什么要是数据结构而不是对话文本？ |
| S7 | 你怎么知道这次改动是变好还是变坏？ |
| S8 | 你的 Agent 最可能被怎么攻击？ |

## 五、五个最容易让你停下来的原因（及对策）

### 1. "效果不如 ChatGPT，是不是我做错了"

**错。** 你的目标是**在特定场景下有用**，不是超越通用模型。

> 对策：把目标写成可测的。不是"回答得好"，而是"20 条评测集召回 ≥ 80%"。
> **有明确目标，就不会拿自己和 GPT 比。**

### 2. "框架那么多，我是不是该用 LangGraph"

**当你问出这句话时，答案是"还不该"。**

> 对策：S2 手写完成后，用框架重写一遍 S2 的循环，**对比才知道框架帮你做了什么**。
> 那时你就有判断力了。

### 3. "我在 S0 卡了两周，是不是不适合"

**S0 的 Python 异步，是前端转过来最大的一道坎。** 卡住是正常的。

> 对策：如果超过 10 天卡在异步，**跳过深度理解，先让它跑起来**。
> 异步的直觉会在 S1 写流式接口时自然建立。

### 4. "做完 S5 觉得项目已经能看了，想直接投简历"

**危险。** 没有 S7 的项目，在"你怎么知道它好用"这一问上必崩。

> 对策：**S7 不是可选项**。哪怕只做 20 条评测集，也比没有强。

### 5. "学到一半发现前面写错了，想重写"

**先别重写。** 新手重写的代价通常是"重写后还是错的，但时间没了"。

> 对策：记进 `notes.md` 的"技术债"清单，**等 S9 一次性重构**。
> 到那时你才知道该怎么改。

## 六、前端转 Agent 的四个心智转变

| 从 | 到 |
|---|-----|
| **确定性**：同输入同输出 | **概率性**：同输入可能不同输出，所以要评测、要重试、要兜底 |
| **状态在内存** | **状态要持久化**：服务会重启，任务会中断 |
| **报错就是 bug** | **报错可能是正常现象**：模型调错工具、JSON 不合法、超时——都要能优雅处理 |
| **功能做完就交付** | **效果要能证明**：没有指标的 Agent 功能，等于没做 |

> **第 4 条是最难的**。前端习惯"能点就行"，Agent 需要"能测才行"。

## 七、每天 10 分钟的"不写代码时间"

| 做什么 | 为什么 |
|--------|--------|
| 回顾 `notes.md` 昨天的踩坑 | 避免重复踩 |
| 看一眼 `docs/` 今天要用的那篇的**局限**章节 | 知道哪些结论不能全信 |
| 想一个"如果这里失败会怎样" | 提前发现设计缺陷 |
| 写一句今天的收获 | 面试时这就是素材 |

> **面试能讲出"我踩过什么坑"的人，比"我学过什么"的人值钱得多。**

## 八、外部资源优先级

**不要一开始就到处找教程。** 按这个顺序：

| 优先级 | 资源 | 用途 |
|--------|------|------|
| **1** | 官方文档（FastAPI / Vue3 / LLM 厂商） | **永远第一**，其他都是二手 |
| **2** | 本仓库 `docs/` 44 篇 | 概念与取舍，已整理好 |
| **3** | 官方示例仓库 | 照抄跑通，再改 |
| **4** | 技术博客 / 视频 | **只用来解决具体问题**，别用来"系统学习" |

> **警惕**：2026 年的 Agent 教程，**一半以上是 2024 年的 API**。
> 看到 `assistant` 消息结构、工具调用格式、模型名不对，**立刻回去看官方文档**。

## 九、git 使用建议（养成习惯）

```bash
# 每个阶段一个分支
git checkout -b feat/s2-agent-loop

# 提交粒度：一个任务一次
git commit -m "feat(agent): 手写 ReAct 循环，支持工具调用与错误回灌"

# 阶段结束合并
git checkout main && git merge feat/s2-agent-loop
```

> **清晰的 commit 历史是简历项目的一部分**——面试官会看。
> 一堆 `update`、`fix`、`123` 的仓库，会让人怀疑代码质量。

## 十、什么时候可以开始投简历

**四个条件全满足**：

- [ ] **有公网可访问的地址**（S8）
- [ ] **至少 3 个真实数字**（S7）
- [ ] **能脱稿讲 3 分钟架构**（S9）
- [ ] **能诚实说出项目 3 个局限**

> **第 4 条最容易被忽略，但最加分。**
> "我这个方案在超过 50 个文件的 PR 上效果会下降，因为分批分析后合并会丢跨文件的上下文关联"——
> **这种回答比"我的项目很完美"可信十倍。**
