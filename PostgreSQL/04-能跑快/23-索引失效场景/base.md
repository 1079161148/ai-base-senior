# 23 索引失效场景 · 完整版

## 0. 怎么用

跑 9/9，再看第 4 节理解「不用索引有时是对的」。

## 1. 概念

优化器基于成本选择路径。索引失效本质是「使用索引的成本估算高于顺序扫描」。

## 2. 机制

```text
列 + 函数 → 索引键不匹配 → 无法用
LIKE '%x' → B-tree 有序性无用 → 无法用
命中率 > 5~10% → 回表成本高 → 优化器选 Seq Scan
```

## 3. API 逐个拆解

| API | 作用 | 注意 |
| --- | --- | --- |
| `lower(col)` 索引 | 函数查询加速 | 查询须写同样表达式 |
| `ANALYZE` | 更新统计 | 大批量导入后必做 |
| `EXPLAIN` | 验证 | 不要猜 |
| `pg_trgm` | 模糊匹配扩展 | 需 CREATE EXTENSION |

## 4. 边界条件

- 返回大部分行时 Seq Scan 更快，这不是 bug。
- `OR` 两侧只有一侧有索引，可能整体走 Seq Scan。
- 空表统计为 0 行，优化器必然选 Seq Scan。

## 5. 注意事项对照表

| 错误写法 / 操作 | 现象 | 正确写法 | 依据 |
| --- | --- | --- | --- |
| 前置% LIKE | Seq Scan | 全文检索 | 实测 |
| 列上函数 | 失效 | 表达式索引 | 实测 |
| 列上运算 | 失效 | 表达式索引 | 实测 |
| 类型隐式转换 | 失效 | 类型对齐 | 实测 |
| 不 ANALYZE | 计划差 | 导入后执行 | 原仓库 06 |
| 命中率高还强求索引 | 更慢 | 接受 Seq | 实测 |
| 小表测索引 | 看不到效果 | 造数据 | 实测 |
| OR 混条件 | 可能全扫 | 拆查询或都建索引 | 实测 |
| 不查计划 | 凭感觉 | EXPLAIN | 第 21 章 |
| 索引后不验证 | 可能没用 | EXPLAIN | 实测 |
| 建重复索引 | 写放大 | 查 pg_stat_user_indexes | 第 22 章 |
| 不清理临时索引 | 干扰后续 | DROP INDEX | 实测 |
| 统计目标太低 | 倾斜列估错 | SET STATISTICS | 实测 |
| 把 Seq Scan 当 bug | 误判 | 看实际耗时 | 实测 |
| 不用参数化查询 | 计划不稳 | 预处理 | 实测 |
| 跳过验收 | 失效不知 | 9/9 再走 | 实测 |
| 把索引当缓存 | 概念错 | 它是数据结构 | 实测 |
| 不记基线 | 优化无对照 | 存计划 | 第 21 章 |

## 6. 最佳实践

先 EXPLAIN 定位，再决定是否建索引；建完再 EXPLAIN 验证。
