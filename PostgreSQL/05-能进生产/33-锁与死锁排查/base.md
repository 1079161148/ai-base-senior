# 33 锁与死锁排查 · 完整版

## 0. 怎么用

## 1. 概念

锁是并发控制的底层机制。按粒度：表级锁（relation）、行级锁（元组 xmax）、事务锁（transactionid）、咨询锁（advisory）。按兼容性：共享与排他。

## 2. 机制

```text
事务 A 持 id=1 行锁 ─┐
                     ├─ 互相等待 → 环 → deadlock_timeout 触发检测 → 回滚一方
事务 B 持 id=2 行锁 ─┘
```

关键事实：PostgreSQL 的行锁记录在元组头的 `xmax` 字段，不进入共享内存的 `pg_locks`。`pg_locks` 里能看到的是表级锁和事务锁。排查行锁阻塞靠 `pg_stat_activity.wait_event_type='Lock'` 加 `pg_blocking_pids()`。

## 3. API 逐个拆解

| API | 作用 | 注意 |
| --- | --- | --- |
| `pg_locks` | 当前锁快照 | 无 tuple 行 |
| `pg_stat_activity` | 会话状态 | 看 `wait_event_type` |
| `pg_blocking_pids(pid)` | 返回阻塞者 PID 数组 | 空数组表示没被阻塞 |
| `pg_advisory_lock(key)` | 应用级锁 | 必须配对 unlock |
| `deadlock_timeout` | 默认 1s | 调太大会拖慢检测 |
| `statement_timeout` | 单语句超时 | 防测试线程永久挂起 |

## 4. 边界条件

- 死锁检测只检查等待图中的环，代价随锁数量上升，所以默认 1 秒才跑一次。
- 被死锁检测选中的事务整事务回滚，不是只回滚冲突语句。
- 咨询锁分会话级和事务级，会话级要显式释放。
- `pg_blocking_pids()` 返回的是直接阻塞者，多层级联需递归展开。

## 5. 注意事项对照表

| 错误写法 / 操作 | 现象 | 正确写法 | 依据 |
| --- | --- | --- | --- |
| 在 pg_locks 找 tuple 锁 | 找不到 | 看等待事件 | 实测 |
| 无限等待锁 | 线程挂起 | statement_timeout | 实测 |
| 死锁后不重试 | 业务失败 | 捕获后退避重试 | 实测 |
| 长事务持锁 | 大面积阻塞 | 缩短事务 | 第 16 章 |
| 咨询锁不释放 | 会话结束才放 | 配对 unlock | 实测 |
| 只查 pg_locks 不看活动 | 定位不全 | 两个视图结合 | 实测 |
| 死锁超时设 0 | 检测过频 | 保持默认或按调优 | 实测 |
| SELECT 不加 FOR UPDATE 就判锁 | 快照读不阻塞 | 明确 FOR UPDATE | 第 18 章 |
| 把行锁当表锁 | 误判影响面 | 理解 xmax 机制 | 实测 |
| 忽略 NOWAIT | 白等 | 用 NOWAIT 快速失败 | 第 18 章 |
| 忽略 SKIP LOCKED | 队列争抢 | 用 SKIP LOCKED | 第 18 章 |
| 不看 wait_event | 不知等什么 | 查等待事件 | 实测 |
| 死锁日志不分析 | 反复发生 | 看服务端日志 | 实测 |
| 高隔离级别下不预期重试 | 序列化失败 | 捕获重试 | 第 17 章 |
| 多级阻塞只看直接者 | 找不全源头 | 递归 pg_blocking_pids | 实测 |
| 跳过验收 | 锁认知错 | 12/12 再走 | 实测 |

## 6. 最佳实践

事务尽量短且按固定顺序访问表；线上用 `statement_timeout` 兜底；发生死锁后捕获并带随机退避重试，而不是让用户直接看到失败。
