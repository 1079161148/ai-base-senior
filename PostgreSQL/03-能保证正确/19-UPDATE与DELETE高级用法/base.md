# 19 UPDATE 与 DELETE 高级用法 · 完整版

## 0. 怎么用

跑 11/11，再看第 4 节理解危险操作怎么防。

## 1. 概念

写操作比查询危险：错了会永久改数据。`RETURNING` 让写操作可观测。

## 2. 机制

```text
UPDATE → 找行 → 计算新值 → 检查约束 → 写堆表 → 更新索引 → RETURNING
```

## 3. API 逐个拆解

| API | 作用 | 注意 |
| --- | --- | --- |
| `SET` | 赋新值 | 可引用旧值 |
| `FROM` | 跨表取数 | 必须关联 |
| `RETURNING` | 返回结果 | INSERT/UPDATE/DELETE 都有 |
| `TRUNCATE` | 清空 | 可重置序列 |

## 4. 边界条件

- `UPDATE ... FROM` 若关联不唯一，一行可能被多次更新，结果不确定。
- `DELETE` 不重置序列，会留 id 空洞。
- `RETURNING` 拿的是更新后的值。

## 5. 注意事项对照表

| 错误写法 / 操作 | 现象 | 正确写法 | 依据 |
| --- | --- | --- | --- |
| 忘 WHERE | 全表更新 | 先 SELECT 验证 | 原仓库 04 |
| DELETE 当 TRUNCATE | 序列不重置 | 按需求选 | 原仓库 04 |
| UPDATE FROM 无关联 | 笛卡尔 | 加 WHERE | 实测 |
| RETURNING 用旧值 | 拿到新值 | 理解语义 | 实测 |
| 无备份执行批量写 | 无法恢复 | 第 20 章 | 原仓库 07 |
| 表达式更新溢出 | 数值越界 | 检查范围 | 实测 |
| 大表批量更新 | 膨胀 | 分批 | 原仓库 07 |
| 不测影响行数 | 改多改少不知 | 用 RETURNING | 实测 |
| TRUNCATE 被外键阻塞 | 依赖错误 | CASCADE | 原仓库 02 |
| 更新主键 | 外键级联 | 谨慎 | 实测 |
| 子查询返回多行 | 报错 | 聚合或 LIMIT | 第 13 章 |
| 不命名约束 | 报错难懂 | 显式命名 | 实测 |
| 事务太大 | 锁久膨胀 | 分批提交 | 实测 |
| 不查执行计划 | 更新慢 | 第 21 章 | 原仓库 06 |
| 跳过验收 | 写错不自知 | 11/11 再走 | 实测 |
| 用 REPLACE 代替 UPDATE | PG 不支持 | ON CONFLICT | 第 08 章 |
| 把 RETURNING 当游标 | 语义混 | 它是一组行 | 实测 |
| 不清理测试数据 | 污染后续 | 独立 schema | 实测 |

## 6. 最佳实践

任何不带 WHERE 的写操作都先 `SELECT count(*)` 确认范围，并在事务里执行。
