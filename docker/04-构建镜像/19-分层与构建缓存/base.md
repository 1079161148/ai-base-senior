# 19 分层与构建缓存 · 完整版

## 0. 怎么用

跑 8/8。本章用真实构建日志与层 digest 验证缓存复用与失效。

## 1. 概念

镜像由层叠加而成，层不可变。构建时 Docker 为每条指令计算 cache key（命令 + 父层 digest + 文件校验和），命中则直接复用，不命中则从该层起重算。

## 2. 机制

```text
FROM → 层1
COPY a → 层2 (key: sha256(a) + 层1)
RUN x  → 层3 (key: "x" + 层2)
COPY b → 层4 (key: sha256(b) + 层3)
RUN y  → 层5 (key: "y" + 层4)

改 b → 层4 key 变 → 层4、层5 重建；层1–3 仍复用
```

## 3. 逐个拆解（本机实测）

| 场景 | CACHED 数 | 层 digest |
| --- | --- | --- |
| 首次 | 0–1 | 全新 |
| 无改动 | 5 | 与首次完全相同 |
| 改 `step2.txt` | 5 | 末层变化，前面不变 |
| `--no-cache` | ≤1 | 全部重算 |

构建历史 8 层；`RUN` 写入的 `build.log` 内容固化进镜像。

**镜像 ID 陷阱**：Docker 29 的 BuildKit 每次构建都会重新生成 attestation manifest，所以 `.Id` 每次都不同，即使所有层都复用了。判断缓存要看 `RootFS.Layers`。

## 4. 边界条件

- `COPY` 的缓存 key 是**文件内容**，不是 mtime；touch 不改内容不会失效。
- `RUN` 的缓存 key 是命令字符串，改一个空格就失效。
- 同一 `RUN` 里 `apt update && apt install` 才能保证索引与安装一致。
- 多阶段构建的中间阶段也参与缓存，但 CI 跨机器需要 `--cache-from`/`--cache-to`。
- `--no-cache` 只影响构建缓存，不影响已拉取的基础镜像层。

## 5. 注意事项对照表

| 错误做法 | 现象 | 正确做法 | 依据 |
| --- | --- | --- | --- |
| `COPY . .` 在依赖安装前 | 改代码即重装依赖 | 先拷清单再拷代码 | 实测 |
| 用镜像 ID 判断缓存 | 误以为没缓存 | 看层 digest/日志 | 实测 |
| `apt update` 单独一层 | 装到旧版本 | 同一 RUN 合并 | 官方 |
| 不清理包缓存 | 镜像变大 | `rm -rf /var/lib/apt/lists/*` | 第 20 章 |
| 小改动就 `--no-cache` | 浪费时间 | 先看 CACHED | 实测 |
| 多阶段不导出缓存 | CI 慢 | cache-from/to | 最佳实践 |
| `.dockerignore` 缺失 | 上下文巨大 | 见第 20 章 | 实测 |
| 频繁改基础镜像 tag | 全部失效 | 固定 digest | 第 22 章 |
| 忽略构建日志 | 不知为何慢 | 看 CACHED 分布 | 实测 |
| 跳过验收 | 缓存原理不清 | 8/8 再走 | 实测 |

## 6. 最佳实践

Dockerfile 顺序：基础镜像 → 系统依赖 → 语言依赖清单 → 安装依赖 → 应用代码。配合 `.dockerignore` 与多阶段构建。
